# 要件の機能分解（区間外）

新しい要件（入力文書）が来たときに回す、区間 A〜E の連鎖に含まれないコマンド。既存の機能マップに追記・まとめるのが役目で、機能ごとの未確定事項の解消は行わない。

## 前提

- 入力文書は、引数で渡されたパス。**引数が省略されたときの既定は `temp/initial-design.md`**。既定の文書が存在しなければ、別のファイルを推測で補完せず、ユーザーに入力文書のパスを尋ねる。
- 入力文書は大きいので、丸ごと読まない。大きいファイルの読み方は [読み込みの規律](../tsod-workflow/references/reading-discipline.md) に従う（目次と見出しで構成を掴み、機能に分けられる節ごとに読む）。
- `specs/feature-map.md` が既に存在する場合は上書きではなく、既存の機能一覧に追記・更新する（既存の機能 ID と重複しない新規 ID を採番する）。無ければ新規に作る。

## 手順

1. 入力文書を読む。
2. 大規模要件を、単独でデモできる縦切りの機能単位へ分解する。画面を持たない機能（ソルバーやマスターデータのパイプラインなど）も、単独で検証できる単位に切る。
3. `specs/feature-map.md` を次の形式で書く。状態列は実装の進捗を示し、当該機能の区間 E（ドリフト検査）で更新する。

```markdown
### 機能マップ
| 機能ID | 名称 | 1行の価値 | 優先度 | 想定サイズ | 状態 |
|---|---|---|---|---|---|
| 001 | ... | ... | P0/P1/P2 | S/M/L | 未着手 |

### 依存
| 機能 | 直接の依存 | 備考 |
|---|---|---|
| 002 yyy | 001 | |
```

状態列の値は `未着手` または `` 済（`specs/NNN-slug`） `` のいずれかを書く。

機能同士の依存は、直接の依存だけを表で持つ（見込み）。実装済みの機能は、各 `spec.md` の「依存する機能ID」が正。この表は機能同士の依存であり、1機能の中のタスクを並列にしてよいかの根拠にはならない（並列化の条件は `.claude/skills/tsod-build/SKILL.md`「委譲」節）。

4. 分解の過程で出た曖昧点を `specs/open-questions.md` に書く。ファイルが無ければ新規に作り、冒頭に「次の番号: Q1」の行を置く。Q 番号は、冒頭に書かれた「次の番号」から振る（既存の最大番号の次。`Q1` から始め直さない。番号は永久欠番で再利用しない）。振ったら冒頭の「次の番号」も更新する。

```markdown
## 要確認事項
- [ ] Q<次の番号>: ...（仮: ...）
```

計画に入る前に曖昧点を洗い出すのが目的である。`specs/open-questions.md` の運用の正は `.claude/rules/specs-authoring.md`（転記しない）。

## 終わりに

追記・更新した `specs/feature-map.md`・`specs/open-questions.md` の差分を提示し、追記内容の確認を AskUserQuestion で1回だけ取る（ゲートではない。修正があれば反映する）。

確認後、「機能ごとの開発は `/tsod-spec NNN`（区間 A・推奨 Opus）から始める。未確定事項はそこで決定する」と案内して終わる。
