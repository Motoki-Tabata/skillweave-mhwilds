# TSOD の原典との違い（設計上の理由）

`docs/method/` の TSOD の原典は、手法を導入したときの資料をそのまま置いたもので、現行運用の正ではない。現行の手順の正は `tsod-workflow/SKILL.md` の区間表で、この文書は、その運用が原典とどこで違うかと、その設計上の理由だけを書く。main への直接 push を防ぐ仕組み（Ruleset と pre-push の併用）は、`README.md` の「main への直接 push を防ぐ」節が正。

違いは次の4点で、いずれも `SKILL.md` の区間表の行と対応している。

| 違い | 区間表での位置 | 設計上の理由 |
|---|---|---|
| 画面設計とテーブル設計の工程を足した | 区間 B（`/tsod-screen-table`。ゲート B-1・B-2） | 原典は、薄仕様の次に計画とタスク分解へ進む。このプロジェクトは画面を持つ PWA と永続化を持つ API の両方を作るので、画面の項目・状態と、テーブルの正規化・命名・属性辞書との整合は、タスクを切る前に人間と確定させないと、区間 D の実装役が設計判断を抱え込む。UI もテーブル変更も無い機能は、区間 B を「該当なし」と記録して飛ばせるので、小さな機能の負担は増えない。 |
| 人間の承認ゲートを足した | 区間表の「ゲート」列（A-1・A-2・B-1・B-2・C-1・D-1・E-1・E-2） | 原典は、検証ゲートの後に人間が受け入れる1か所を中心にする。エージェントが書く量が多いほど、下流で見つかる誤りの手戻りが大きいので、手戻りの大きい判断（未確定事項の決定・薄仕様・画面・テーブル・計画とタスク分解・実装の受入・マージ・ドリフトの是正）の直前に、ゲートを1回ずつ置く。ゲートは AskUserQuestion の1回の問いにし、承認を handoff に記録する。 |
| 作業を区間 A〜E に分け、区間ごとに新しいセッションで始める | 区間表の全行・「原則」節 | 原典は、ヒアリングから仕様、計画、実行までを1つの流れとして書く。1機能の全工程を1つの会話で進めると、文脈が膨らんだまま下流の判断を重ね、前の区間の議論の細部に引きずられる。区間の切れ目で会話を閉じ、引き継ぎを `specs/NNN-<slug>/handoff.md` に限ると、次の区間は必要な事実だけから始められ、推奨モデルも区間ごとに選べる（設計判断の区間は Opus、定型の区間は Sonnet）。 |
| 未確定事項の決定を、機能ごとの区間 A の最初の工程に置いた | 区間 A のゲート A-1（`/tsod-discover` は決定しない） | 原典は、ヒアリングの段階で機能マップと曖昧点を出し、曖昧点を計画の前に片付ける。要件の入力文書から全機能分の曖昧点を先に決めると、まだ着手しない機能の決定を、情報が少ない時点で固定してしまい、後で覆る。`/tsod-discover` は曖昧点の洗い出しと `specs/open-questions.md` への記録までにとどめ、決定は、その機能の `/tsod-spec NNN` の最初の工程（ゲート A-1）で、その機能を実装する直前の情報で行う。決定は `decisions.md` に移し、`open-questions.md` には未解消の項目だけを残す。 |
