# 001: solver-spike

## 目的 / ユーザーストーリー
開発者（オーナー）として、HiGHS の WASM 版（npm `highs`）で実データ規模の ILP（必須スキル・防具5部位・護石・スロット Lv 別の装飾品個数）が数秒以内に解けるかを、ソルバー本体（003）と画面（004）の前に確かめたい。ソルバーの方式は後続の全機能の前提になる最大の技術リスクなので、先に潰す。ここで書く定式化と HiGHS の呼び出しは捨てずに `packages/solver` に残し、003 で拡張する（decisions.md Q1）。

用語:
- 構成: 防具5部位（頭・胴・腕・腰・脚の各1つ）と護石1つの組と、それに付けるスロット Lv 別の装飾品の個数。
- 検索1回: 構成を最大 30 件まで列挙する一連の求解（decisions.md Q8）。

## 受入基準（EARS記法）
- THE system SHALL `packages/solver` に、必須スキル（スキルと下限レベル）・部位ごとの防具候補・護石候補・固定の武器（スロットとスキル）・装飾品候補を受け取り、必須スキルの合計レベルがすべて下限以上になる構成を HiGHS で求める関数を提供しなければならない。
- THE system SHALL 装飾品の個数を、武器用・防具用のスロットを区別し、スロット Lv 以下の装飾品だけを付けられる制約のもとで決めなければならない。
- THE system SHALL 防御力の合計を最大化する構成を求めなければならない（列挙の各回で最適性の証明まで解くため、もっとも重いケースを測る）。
- WHEN 構成が見つかったとき THE system SHALL 得た防具と護石の組を除く制約を足して解き直し、30 件に達するか解が尽きるまで構成を列挙しなければならない。
- THE system SHALL 1回の検索の中で、防具と護石の組が同じ構成を2回返してはならない。
- IF 条件を満たす構成が1つも無いとき THEN システムは、構成を返さずに解なしであることを返さなければならない。
- THE system SHALL 返すすべての構成について、ソルバーと独立に数え直した必須スキルの合計レベルとスロットの使用数が、制約を満たしていなければならない（テストで検算する）。
- THE system SHALL シード固定の合成データ生成器を `packages/solver/src/test/` に持ち、同じシードから同じデータを生成しなければならない。件数とスロット・スキルの分布は decisions.md Q2 の MHDB 実測値（上位防具 582・装飾品 361・スキル 179・生産護石 187）に合わせ、出典（取得日）をコードに書かなければならない。
- WHEN 測定を実行したとき THE system SHALL 上位防具の全件を候補にし、必須スキル 3／6／10 個 × 解あり／解なしの各ケースについて、検索1回の合計時間と1回の求解ごとの時間を出力しなければならない（HiGHS の初期化は時間に含めない）。
- THE system SHALL 測定結果（ケースごとの時間、合計時間の最大と 3 秒の合格基準に対する合否、測定環境、HiGHS の版）と HiGHS の採否を `design/tech-stack.md` に記録しなければならない。
- IF 合計時間の最大が 3 秒を超えたとき THEN システムは、必須スキルに寄与しない防具を部位ごとに代表へまとめる縮約を1回だけ加えて再測定し、縮約の前後の両方の結果を記録しなければならない。
- IF 縮約を加えても 3 秒を超えたとき THEN システムは、代替（別の ILP ライブラリ・自前の探索）の選定を `specs/open-questions.md` に新しい Q として起票し、001 を「不合格」の結論で閉じなければならない。
- THE system SHALL 時間の測定を CI の検証コマンドで実行してはならず、CI で実行するテストで時間を検査してはならない（環境で揺れるため）。
- THE system SHALL `packages/solver/src/main` のコードを DOM・Node の API と API の型に依存させてはならない。

## スコープ外
- シリーズ／グループスキル・部位の固定と除外・武器の探索・装飾品の具体的な配置（後処理）・タイムアウトとキャンセル・`masterVersion` の照合・Worker のメッセージ型（003）
- 実データ（002 の `master-<version>.json`）での再測定（003 の受入基準に入れる）
- ブラウザ（Worker）での測定（004）
- 鑑定護石を候補に含めること（005）。001 の護石候補は生産護石だけ
- 火力（`expectedDamage`）の最大化（006）。001 の目的関数は防御力の合計の最大化だけ
- 下位防具を候補に含めること
- 装飾品の所持数の制限（001 ではすべての装飾品を必要なだけ持っているものとする）
- 不合格時の代替ライブラリ・自前の探索の実装
- `temp/solver-types.ts` の型の全量の移設（001 で使う分だけを移す）

## 契約差分
- なし（API を持たない。ソルバーはブラウザ内で動く）
