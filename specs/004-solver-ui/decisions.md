# 004 solver-ui の決定記録

## Q4（決定: 2026-10-06）
- 問い（`open-questions.md` からの移設）: UI を英語にも対応するか。マスターの辞書は ja/en を生成する（§7.2）が、画面の文言の多言語化はどこでも決まっていない（仮: 画面は当面日本語のみ。辞書は en も生成して配信する）
- 決定: 仮のとおり。画面の文言は日本語だけにし、004 の画面は ja の辞書だけを読む。en の辞書は `packages/data` が生成し続けるが、画面では使わない。

## Q20（決定: 2026-10-06）
- 問い（`open-questions.md` からの移設）: 実データでの検索 1 回が基準の 3 秒を超える（003 の測定。`design/tech-stack.md`「HiGHS の実データでの再測定（003 solver-engine）」）。必須スキル 10 個・解ありで最大 7.7 秒、6 個で約 4.1 秒。1 求解の時間は後ろの件ほど長い（最初の数件は約 30〜60 ms、最後の数件は約 600〜770 ms）。004 の着手前に、どの対策を取るか決める（案: 防具の候補の縮約［必須スキルに寄与しない防具のまとめ］・1 回の検索で求める件数の既定を減らす・件数の上限を下げる・1 件ずつ画面に出して 3 秒の基準を「最初の 1 件まで」に読み替える・除外の行の入れ方を変える。仮: 案ごとに実データで再測定して決める）
- 決定: 1 回の検索で求める件数（`maxResults`）の既定を 10 件にし、画面で 1〜30 件を選べるようにする（上限の 30 件は 003 Q15 のまま）。3 秒の基準は「既定の件数での検索 1 回」に読み替える。ソルバーは変更しない。
- ブラウザの Worker 上での時間（001・003 で未測定）を 004 で測り、`design/tech-stack.md` に記録する。CI では測らない。
- 判断材料（2026-10-06 に 003 の測定ハーネスを再実行。Node・`maxResults` 30・各ケース 3 回）: 件数ごとの累積時間は、10 件までが k=3 で 147〜260 ms、k=6 で約 0.28 秒、k=10 で約 0.32 秒。30 件までは k=10 で約 3.9 秒（10/04 の 7.7 秒の約半分）。ソルバーのコードは 10/04 から変わっていないため、測定環境の負荷の差と見ているが、切り分けていない。
- 採らなかった案: 1 件ずつ画面に出す案は、進捗のメッセージ（件数だけ）に構成を載せる変更が `packages/solver` に要る。防具の候補の縮約は定式化を変える。いずれも 10 件の既定で基準に収まるため、今は行わない。

## Q21（決定: 2026-10-06）
- 問い: 防具の候補から下位の防具を外すか（003 Q15 で、呼び出し側の 004 が除外の指定で決めることになっていた）。
- 決定: 防具にランク（下位・上位・マスター）を持たせ、画面で候補にするランクを複数選べるようにする。既定では、マスターに含まれる最も高いランクだけを候補にする（ワイルズの現行のデータでは上位だけ。アセンダンスでマスターランクの防具が入ったら、マスターランクだけ）。選ばれていないランクの防具は、ソルバーへの除外の指定で外す（ソルバーは変更しない）。
- ランクは `packages/data` のパイプラインで防具に付ける。MHDB の防具にはランクの項目が無くレア度だけがあるため、レア度とランクの対応表をパイプラインの設定に持つ（現行のデータでは 1〜4 が下位、5〜8 が上位）。マスターランクの対応は、アセンダンスのデータが MHDB に入ったときに対応表を直して決める。
- マスターの内容が変わるため、マスターの版を上げる（`design/master-data.md`「出力しようとする版のファイルが既にあり中身が異なるときは、版を上げる」）。
- 採らなかった案: `apps/web` の定数でレア度からランクを決める案は、ゲームの知識が web に入り、アセンダンスで web を直すことになるため採らない。

## Q22（決定: 2026-10-06）
- 問い: 部位の固定・除外（ソルバーは 003 で対応済み）の入力 UI を 004 に含めるか。
- 決定: 004 のスコープ外にする。004 の入力は、武器・必須スキル・目的関数・件数・候補にする防具のランク（Q21）だけにする。固定・除外の入力 UI は、後で `/tsod-discover` で新しい機能として機能マップに追加する。

## Q23（決定: 2026-10-06）
- 問い: 検索条件と結果を端末に保存し、再読み込みの後も残すか。
- 決定: 保存しない。再読み込みすると検索条件は既定値に戻り、結果は消える。端末内の下書き（IndexedDB）は 005 charm-input で初めて導入する。

## Q24（決定: 2026-10-06）
- 問い: 004 で作る e2e の基盤の範囲。
- 決定: Playwright を Chromium だけで動かし、ビルドした web を、実際のマスター（`packages/data/dist/` の現行の版）と実際の HiGHS で検証する。API・DB は起動しない（004 は API を持たない）。CI に e2e ジョブを足す。
- 一括検証（`.claude/skills/tsod-verify/scripts/verify.mjs`）の e2e の段は docker と API を起動する作りで、`CLAUDE.md` の Commands 表には e2e の行が無い。どちらも canon の管理下にあるため、`tasks/lessons.md` に canon への改修要求として起票する（`CLAUDE.md`「e2e の追加」節）。

## Q25（決定: 2026-10-06）
- 問い: 武器種（MHDB の `kind`。例: `charge-blade`）と部位（`head` など）の日本語名をどこに持つか。辞書（`master-<版>.ja.json`）には武器種の名前が無い。
- 決定: 画面の文言として `apps/web` の定数に持つ。武器種と部位はマスターの項目ではなく列挙値で、その表示名は UI の文言として扱う（Q4 で画面は日本語だけにした）。Q21 のランクの区分（どのレア度がどのランクか）はゲームの知識なのでパイプラインに持つが、ランクの表示名（下位・上位・マスター）も同じく `apps/web` の定数に持つ。
