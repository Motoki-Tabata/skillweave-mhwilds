# 005 charm-input の決定記録

## Q3（決定: 2026-10-23）
- 問い（`open-questions.md` からの移設）: 鑑定護石の抽選テーブル（レア度ごとのスキル枠グループ・スロットパターン）は MHDB に無く、攻略サイトのスクレイピングもしないため、人手で YAML に起こすことになる。誰がいつ作るかと、未整備のレア度で 005 の妥当性検査をどう扱うか（仮: 005 の中でオーナーが作る。テーブルがあるレア度だけ検査し、無いレア度は検査せずに登録を受け付ける）
- 決定: 仮のとおり。005 の中で、オーナーが起こせたレア度の分だけ `packages/data/overlays/` の `appraisedCharm` に書き、マスターの版を上げて `dist/` を再生成する。テーブルが無いレア度の護石は照合せずに登録を受け付け、「未検査」と示す。
- 照合の仕組みのテストは、実データではなくテスト用のテーブル（フィクスチャ）で行う。オーナーの入力がどのレア度まで済んだかは 005 の完了条件にしない。

## Q26（決定: 2026-10-23）
- 問い（`open-questions.md` からの移設）: ライトテーマへの切り替えの導線。トークンと既定値（`index.html` でダークを既定にし、`localStorage` の `swv-theme` が `light` のときだけ外す）は入れたが、画面に切り替える手段が無く、ライトテーマは実質使えない（仮: 次に画面設計を行う機能（005 charm-input）で、ヘッダーにトグルを置く。OS の設定に追従するかもそこで決める）
- 決定: 005 でヘッダーにダークとライトを切り替えるトグルを置く。既定はダークのまま、OS の設定には追従しない。選んだテーマは今の仕組みのまま `localStorage` の `swv-theme` に保存する（端末ごとの好みであり、サーバーへは送らない）。トグルの見た目と位置は区間 B で決める。

## Q29（決定: 2026-10-23）
- 問い: 手入力した護石が抽選テーブルに合わないとき、保存を拒否するか。
- 決定: 拒否しない。どの点が合わないかを示し、ユーザーが確認したうえで保存できる。一覧にも「テーブル不一致」と示し、ソルバーの候補には含める。テーブルは手作業で起こすため、テーブルの誤りで実在の護石が登録できなくなるのを避ける。
- 構造上の誤り（Q32 の制約に反するもの）は、テーブルの有無にかかわらず保存を拒否する。

## Q30（決定: 2026-10-23）
- 問い: 生産護石（マスターの `charms`）を 005 でソルバーの候補にするか。現状の `SolverCharm.id` は `Uuid` 型で、マスターの `CharmId`（`ch:...`）を渡すには `packages/solver` の型の変更が要る。
- 決定: 005 の対象外にする。005 は鑑定護石の手入力だけを扱う。生産護石を候補にする方式は未確定事項 Q31 として `open-questions.md` に残す。

## Q32（決定: 2026-10-23）
- 問い: 登録した護石の保存の仕方、ソルバーへの渡し方、入力できる値の範囲（構造上の制約）。
- 決定（保存）: 護石は端末内の IndexedDB に保存し、ログインもサーバーへの送信もしない。IndexedDB はライブラリを使わずネイティブの API で扱う（依存を増やさない）。ID はクライアント採番の UUIDv7 で、自前で実装する（`design/data-model-standard.md`「主キー・採番方針」）。保存する形は、010 charm-save のサーバー側と同じにする（`design/data-model-standard.md`「所有者と監査カラム」）。項目の確定は区間 B で行う。
- 決定（渡し方）: 登録した護石のうち、構造上の制約を満たすものをすべて（未検査・テーブル不一致を含む）ソルバーの候補にする。護石ごとに候補から外す切り替えは設けない。マスターの更新で、護石のスキルが現行のマスターに無くなった、または最大レベルを超えた場合は、その護石を候補から外し、一覧でその旨を示す。
- 決定（構造上の制約）: スキルは 0〜3 個で重複がなく、種別が武器スキルか防具スキル（シリーズ／グループスキルではない）で、レベルが 1 以上そのスキルの最大レベル以下。スロットは 0〜3 枠で、各枠が武器用か防具用と Lv 1〜3 を持つ。レア度は 5〜8（`design/master-data.md`「ゲーム仕様の確認結果」）。
- レア度の範囲 5〜8 は、入力の選択肢として `apps/web` の定数に持つ。Q21（004）の考え方ではゲームの知識はパイプラインに持つが、`MasterBundle` の型を変えて版を上げる変更を 005 に持ち込まないため、アセンダンス対応のときに見直す。

## Q33（決定: 2026-10-23）
- 問い: 護石を抽選テーブルとどう照合するか。
- 決定: 護石のレア度のパターン（`AppraisedCharmPattern`）のどれか1つについて、次の2つがともに成り立てば合格とする。スキルの並び順とスロットの並び順は、ゲーム内の表示順として意味を持つ。
  - スキルの i 番目が、パターンの `skillGroups` の i 番目のグループ（`groups` の `skills`）に、同じスキルとレベルで含まれる。`skillGroups` の i 番目が null の枠にはスキルが無い。
  - スロットの並びが、パターンの `slotPatterns` のどれかと（target と Lv の並びで）一致する。
- 照合の結果は「合格」「テーブル不一致（合わない点を添える）」「未検査（そのレア度のテーブルが無い）」の3つとする。照合はブラウザの中で行う純粋な関数とし、016 charm-ocr と 017 reverse-lookup から使えるようにする（置き場は区間 C で決める）。

## Q34（決定: 2026-10-23）
- 問い（区間 B の画面設計で判明）: 護石の入力でスキルを Combobox で選ぶとき、ひらがなで入力しても漢字のスキル名の候補を出せるか。ja の辞書は読みを持たず、武器・防具スキル 137 件のうち 126 件が漢字を含むため、ひらがなとカタカナの変換だけでは引けない。
- 決定: 005 に含める。すべてのスキルの読み（ひらがな）を手作業の overlay で `packages/data/overlays/` に書き、ja の辞書のスキルの項目に読みを出し、マスターの版を上げて `dist/` を再生成する。読みの下書きは区間 D で作り、オーナーが確認する。
- スキル名の検索は、護石の入力と 004 の必須スキルのダイアログで同じ規則にする。入力をスキル名と読みの両方に部分一致で照らし、ひらがなとカタカナ、全角と半角の違いを同一視する。読みが無いスキルは名前だけで照らす。
- 武器名・防具名・装飾品名の読みでの検索は扱わない。overlay と辞書の書式は区間 C で決める。
