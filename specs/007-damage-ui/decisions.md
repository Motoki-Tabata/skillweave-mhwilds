# 007 damage-ui の決定記録

## Q42（決定: 2026-10-24）
- 問い: Q41（`expectedDamage` の検索時間が最大 54974.3 ms で、基準の 3 秒も画面の時間の上限 `SOLVE_TIMEOUT_MS` の 30 秒も超える）の対策を 007 とどう関係づけるか。
- 決定: 007 の対象外にする。対策（原因の切り分け・高速化、006 のゲート D-1 で決めた「2 段目が解なしのとき 1 段目の解を返す縮退」と「実データのテストの `timeoutMs` の明示」）は、`packages/solver` だけを触る独立した機能として 007 の前に置く。機能マップへの追加と ID の採番は `/tsod-discover` で行い、対策の中身はその機能の区間 A で Q41 として決める。
- 007 の区間 B は、その機能のマージの後に始める（007 の区間 A は済ませてある）。対策の結果で 007 の spec の前提（時間切れの扱い・件数・並びの厳密さ）が変わったら、区間 B の前に spec を直す。
- 理由: 原因が未切り分けで作業量が読めず、画面の作業と混ぜると 1〜3 日でマージに届かないおそれがあるため。また、対策の案（件数の既定を下げる・Worker 上での非同期の表示・2 段目の省略）には 007 の画面の前提を変えるものがあり、先に画面設計を固めると手戻りになるため。

## Q43（決定: 2026-10-24）
- 問い: 結果の構成ごとに出す火力の値と、出す条件。
- 決定: 目的関数にかかわらず、どの構成にも期待値と内訳（攻撃力・会心率・会心倍率）の4値を出す。値は `packages/solver` の `evaluateDamage` で、検索したときの武器・構成の発動スキル・有効な条件から計算する。
- 表示の丸め（006 decisions.md Q35 で 007 に委ねたもの）: 期待値と攻撃力は小数第1位、会心率は整数の %、会心倍率は小数第2位。丸めは表示だけで行い、並び順には使わない。
- 属性の期待値は出さない（Q40。006 と同じく物理だけ）。

## Q44（決定: 2026-10-24）
- 問い: 発動条件のトグルの既定と、検索の後にトグルを変えたときの振る舞い。
- 決定: トグルの既定は全オフ（条件付きの効果を数えない。ソルバーの `activeConditionIds` が空のときと同じ）。検索の要求には、検索したときにオンの条件を `activeConditionIds` として渡す。
- 表示中の構成の火力は、検索したときの条件で固定する。検索の後にトグルを変えても表示は変わらず、次の検索から効く（004 の「検索の後に武器の選択を変えても、結果は検索したときの武器で表示する」と同じ扱い）。
- トグルの状態は保存しない（004 decisions.md Q23 の検索条件と同じ）。
- 検索画面の目的関数の選択肢に「火力の最大化」（`maximize: expectedDamage`）を足す（006 decisions.md Q38）。トグルの置き場所と見た目は区間 B で決める。

## Q45（決定: 2026-10-24）
- 問い: スキルの説明文（`levelDescriptions`）と効果の数値の補完をどこに出すか。
- 決定: 次の2か所に出す。
  - 結果の構成の発動スキル: 発動しているレベルの説明文と補完。
  - 必須スキルを選ぶダイアログ: スキルのレベルごとの説明文と補完。
- 補完は `effectsByLevel` のそのレベルの効果から画面で作り、辞書に保存しない（`initial-design.md` §7.4）。条件付きの効果は、条件の名前（辞書の `name`）を添える。効果が無いレベルは補完を出さない。説明文が辞書に無いレベルは説明文を出さない。
- 開閉・展開などの見せ方と、補完の文の書式は区間 B で決める。

## Q46（決定: 2026-10-25）
- 問い: 019 damage-solve-perf の結果（`expectedDamage` の合計時間は最大 37739.4 ms で 3 秒を超え、基準を「1件目までの時間の最大が 3 秒以下」に読み替えた。合格は、進捗の通知に載る構成を画面が1件ずつ出すことが前提。019 decisions.md Q41・`design/tech-stack.md`「HiGHS の expectedDamage の再測定（019 damage-solve-perf・2026-10-24）」）を受けて、検索中に届いた構成を画面に出す範囲。
- 決定: 目的関数にかかわらず、Worker の `progress` のメッセージで届いた構成（`build`）を、届いた順に結果へ足して表示する。各構成の火力も届いた時点で表示する。検索が終わったら、ソルバーが返した結果で置き換える。
- 理由: 進捗の通知の構成は目的関数を問わず同じ形で届く（019 plan D6）ので、表示の経路を1本にできる。他の目的関数は速く終わるので、見た目はほとんど変わらない。

## Q47（決定: 2026-10-25）
- 問い: 逐次表示の途中で検索を取り消したときに、届いた構成をどうするか。
- 決定: 004 の振る舞いを変えない。取り消したら、届いた構成も消して検索前の状態に戻し、取り消した旨のトーストを出す。途中までの構成が欲しいときは、時間切れまで待つ（時間切れのときは見つかった構成を出す）。

## Q48（決定: 2026-10-25）
- 問い: 火力の最大化の時間の上限。画面の上限 `SOLVE_TIMEOUT_MS` は 30 秒で、019 の Node での測定では合計時間の最大が 37739.4 ms（必須スキル 3 個・解あり）と上回る。
- 決定: 30 秒のまま、目的関数にかかわらず同じ上限にする。10 件に届かないときは、004 の時間切れの表示で、見つかった構成と打ち切られた旨を出す。
- 理由: 逐次表示があるので、待ち時間の体感は1件目までの時間で決まる。目的関数ごとに上限を変えると、検索の振る舞いの説明が増える。

## Q49（決定: 2026-10-25）
- 問い: ブラウザの Worker 上での `expectedDamage` の1件目までの時間（019 のスコープ外で、007 に持ち越された。Node では最大 2609.6 ms・余裕約 0.4 秒）を 007 で測るか。
- 決定: 007 で測る。004 の画面の測定（`pnpm --filter @swv/web run measure`）と同じ方式で、019 と同じ条件（実データ・条件をすべて有効・マスターの先頭の武器・護石なし・件数 10・必須スキル 3／6／10 個 × 解あり／解なし・各 3 回）の1件目までの時間と合計時間を測り、`design/tech-stack.md` に記録する。CI では測らない。
- 1件目までの時間の最大が 3 秒を超えたときは、対策を `specs/open-questions.md` に新しい Q として起票し、007 はその記録をもって進めてよい（019 decisions.md Q41 と同じ扱い）。
