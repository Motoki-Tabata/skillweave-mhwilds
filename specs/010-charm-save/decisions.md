# 010 charm-save の決定記録

## Q58（決定: 2026-10-27）
- 問い: ログインしているとき、護石の画面と検索の候補はどの護石を使うか。端末内（IndexedDB）の護石をどう扱うか。
- 決定: ログインしているときは、護石の画面も検索の候補も、サーバーに保存した護石（アカウントの護石）だけを使う。端末内の護石は消さず、サーバーへ送らず、ログインしている間は表示しない。ログアウトすると、ふたたび端末内の護石を表示する。画面には、いまの保存先（この端末かアカウントか）を示し、ログインしている間に端末内に護石が残っていればその旨を示す（文言と置き場は区間 B で決める）。未ログインのときと、認証状態を取得できないとき（009 の「取得できない」）は、005 のとおり端末内の護石を使う。
- 理由: 端末内の護石のサーバーへの取り込みは 014 guest-draft-import で一方向・一回きりで行う（`temp/initial-design.md` §2.1）。両方を並べて検索の候補に使うと、014 で取り込んだ後に同じ護石を二重に数えるおそれがあり、014 との境目もあいまいになる。

## Q59（決定: 2026-10-27）
- 問い: 護石を保存する API の形と、サーバーが受け持つ項目。
- 決定: API は次の4つとし、すべてログインを要する（未ログインは 401）。状態を変える要求は CSRF トークンを要する。
  - 一覧: ログインしているユーザーの、削除していない護石をすべて返す。並びは ID の降順（新しい順）。ページングはしない（Q62）。
  - 作成: 本文に ID（クライアントで採番した UUIDv7）・護石の内容（`payload`）・スキーマ版を受け取り、保存した護石を返す。ID が既存の行（自分の行・他のユーザーの行・削除済みの行を問わない）と衝突したら 409 で拒否する。
  - 更新: 本文に護石の内容・スキーマ版・行バージョン（`version`）を受け取る。行バージョンが一致すれば更新して保存後の護石を返し、一致しなければ 409 で拒否する（Q60）。自分の削除していない行が無ければ 404 を返す（他のユーザーの行も 404 とし、存在を漏らさない）。
  - 削除: 論理削除（`deleted_at`）にする。行バージョンは照合しない。呼んだ後に、自分の削除していない行としてその ID が残っていなければ成功（204）とする（削除済み・存在しない・他のユーザーの行でも 204。他のユーザーの行は変えない）。
  - 作成日時・更新日時・行バージョンはサーバーが管理し、クライアントが送った値は使わない（`design/data-model-standard.md`「所有者と監査カラム」）。応答には、端末側と同じ形（ID・内容・スキーマ版・作成日時・更新日時）に行バージョンを加えて返す。
- 理由: 作成と更新を分けると、クライアント採番の ID で新しい行を作るのか既存の行を変えるのかがサーバー側で明確になり、他のユーザーの行との ID の衝突の拒否（`design/data-model-standard.md`「主キー・採番方針」）も作成の側だけで扱える。削除を何度送っても同じ結果にすると、通信の失敗の後に送り直しても安全になる。

## Q60（決定: 2026-10-27）
- 問い: 別の端末での変更との競合、ログインの期限切れ、通信の失敗のとき、画面はどう振る舞うか。
- 決定:
  - 更新が行バージョンの不一致（409）で拒否されたら、上書きせず、別の端末で変更されたことを知らせ、一覧をサーバーから読み直す。更新しようとした護石が別の端末で削除されていた（404）ときも、その旨を知らせて読み直す。
  - 削除は行バージョンを照合しない（Q59）。別の端末で編集・削除された護石も、そのまま消える。
  - 護石の API が 401 を返したら、保存・削除はせず、ログインの有効期限が切れたことを知らせ、ヘッダーを未ログインの表示に戻し、一覧を端末内の護石に切り替える。
  - ログインしているのに一覧を取得できない（API に届かない・401 以外のエラー）ときは、読み込めなかったことと再読み込みの操作を示し、護石なしの検索は引き続き使えるようにする（005 の、端末内の保存の失敗のときと同じ扱い）。保存・削除の失敗はトーストで知らせ、一覧を変えない。
  - 保存の要求を後で送り直す待ち行列と、サーバーの一覧の端末への写し（キャッシュ）は持たない。書き込みはオンラインのときだけ行う（`temp/initial-design.md` §2.1）。オフラインでの閲覧は 018 pwa-offline で扱う。
- 理由: 楽観的ロックで競合を検出する方針（`design/data-model-standard.md`「楽観的ロック」）に従う。401 のときに未ログインに戻すと、009 のヘッダーの表示と一覧の保存先が食い違わない。

## Q61（決定: 2026-10-27）
- 問い: サーバーは、受け取った護石の内容をどこまで検査するか。
- 決定: マスターに依らない構造だけを検査し、反していれば 400 で拒否する。ID は UUIDv7 の形式、スキーマ版は 1、レア度は 5〜8、スキルは 0〜3 個（スキル ID は `sk:` に数字が続く形式で重複しない。レベルは 1 以上の整数）、スロットは 0〜3 枠（種別は `weapon` か `armor`、Lv は 1〜3）。スキルの存在・最大レベル・シリーズ／グループスキルの除外の検査と、抽選テーブルとの照合は、005 のとおり Web で行う。
- 理由: マスターデータは DB に置かず、静的な JSON として Web にだけ配る（`temp/initial-design.md` §2）。サーバーにマスターを持たせると、マスターの版の更新に API の配布が連動してしまう。構造の検査だけで、壊れたデータや過大なデータの書き込みは防げる。

## Q62（決定: 2026-10-27）
- 問い: 1 ユーザーが保存できる護石の件数に上限を設けるか。
- 決定: 010 では上限を設けない。一覧は全件を一度に返し、ページングはしない。一般公開（014 guest-draft-import）の前に見直す。
- 理由: いまはフレンドだけに公開する段階で、護石の件数は多くても数百件と見込まれる。上限とその超過時の画面の扱いを加えるほどの必要がまだ無い。
