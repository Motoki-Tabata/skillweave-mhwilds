# 010: charm-save

## 目的 / ユーザーストーリー
Discord でログインしたプレイヤーとして、登録した鑑定護石をサーバーに保存し、PC とスマホなどの複数の端末で同じ護石の一覧を使って構成を探したい。ログインしていないときは、これまでどおり端末内（IndexedDB）に保存して使える（005）。端末内の護石のサーバーへの取り込みは 014 で行い、010 では行わない（`temp/initial-design.md` §2.1）。

用語:
- アカウントの護石: ログインしているユーザーがサーバーに保存した護石。
- 端末内の護石: 005 で端末内の IndexedDB に保存した護石。
- 行バージョン: 護石の行ごとにサーバーが持つ版（`version`）。別の端末での変更との競合の検出に使う（`design/data-model-standard.md`「楽観的ロック」）。

## 受入基準（EARS記法）
- AC-1: WHILE ログインしているとき THE system SHALL 護石の画面の一覧と検索の護石の候補に、アカウントの護石だけを使わなければならない。端末内の護石を表示・送信・削除してはならない（decisions.md Q58）。
- AC-2: WHILE ログインしているとき WHEN 護石を登録・編集・削除したとき THE system SHALL それをサーバーに保存し、同じアカウントでログインした別の端末でも同じ一覧を表示しなければならない。新しい護石の ID はクライアントで採番した UUIDv7 とし、入力・照合・候補の判定は 005 と同じに行わなければならない。
- AC-3: WHERE 未ログイン、または認証状態を取得できないとき THE system SHALL 005 のとおり端末内の護石を使わなければならない。WHEN ログアウトしたとき THE system SHALL 画面を移らずに、一覧と検索の候補を端末内の護石に切り替えなければならない（decisions.md Q58）。
- AC-4: THE system SHALL 護石の画面に、いまの保存先（この端末かアカウントか）を示し、ログインしている間に端末内に護石が残っていればその旨を示さなければならない（decisions.md Q58）。
- AC-5: THE system SHALL 護石の一覧・作成・更新・削除の API をログインを要するものとし、一覧は自分の削除していない護石だけを ID の降順で全件返し（ページングしない）、作成日時・更新日時・行バージョンをサーバーで管理して、応答は端末内の護石と同じ形に行バージョンを加えて返さなければならない。他のユーザーの護石を返したり変えたりしてはならない（decisions.md Q59・Q62）。
- AC-6: IF 未ログインのまま護石の API を呼んだとき THEN API は 401 を返し、状態を変える要求が CSRF トークンを持たないときは拒否して、護石を変えてはならない。
- AC-7: IF 作成の ID が既存の行（自分・他のユーザー・削除済みを問わない）と衝突したとき THEN API は 409 で拒否し、既存の行を変えてはならない（decisions.md Q59）。
- AC-8: IF 更新の行バージョンがサーバーの行と一致しないとき THEN API は 409 で拒否して上書きせず、Web は別の端末で変更されたことを知らせて一覧をサーバーから読み直さなければならない。更新する護石が自分の削除していない行に無いときは、API は 404 を返し、Web は別の端末で削除されたことを知らせて読み直さなければならない（decisions.md Q59・Q60）。
- AC-9: WHEN 護石を削除したとき THE system SHALL 論理削除（`deleted_at`）にし、行バージョンを照合せず、削除済み・存在しない・他のユーザーの ID でも 204 を返さなければならない。他のユーザーの行を変えてはならない（decisions.md Q59）。
- AC-10: IF 作成・更新の内容がマスターに依らない構造の制約（ID は UUIDv7・スキーマ版は 1・レア度は 5〜8・スキルは 0〜3 個で ID は `sk:` に数字が続く形式・重複なし・レベルは 1 以上・スロットは 0〜3 枠で種別は `weapon` か `armor`・Lv は 1〜3）に反するとき THEN API は 400 で拒否し、保存してはならない（decisions.md Q61）。
- AC-11: IF 護石の API が 401 を返したとき THEN Web は、ログインの有効期限が切れたことを知らせ、ヘッダーを未ログインの表示に戻し、一覧と検索の候補を端末内の護石に切り替えなければならない（decisions.md Q60）。
- AC-12: IF ログインしているのにアカウントの護石の一覧を取得できないとき THEN システムは、読み込めなかったことと再読み込みの操作を示し、護石なしの検索を使えるようにしなければならない。保存・削除に失敗したときは、トーストで知らせて一覧を変えず、要求を後で送り直してはならない（decisions.md Q60）。
- AC-13: THE system SHALL アカウントの護石を Flyway のマイグレーションで作る `charms` テーブルに保存し、その項目を `design/attributes.yaml` に確定しなければならない。
- AC-14: THE system SHALL API のテスト（Testcontainers）で、作成・一覧・更新・削除、他のユーザーの護石の隔離、ID の衝突、行バージョンの不一致、構造の制約の違反、未ログインの 401、CSRF トークンの無い要求の拒否を検証しなければならない。
- AC-15: THE system SHALL Playwright（Chromium）の e2e テストで、API の応答を差し替えて、ログインしているときに護石を登録すると一覧に出て検索の候補に使われること、ログアウトすると端末内の護石に切り替わること、更新が 409 のときに知らせて読み直すことを検証しなければならない。

## スコープ外
- 端末内の護石のサーバーへの取り込み（014 guest-draft-import）
- オフラインでの閲覧、保存の要求の送り直しの待ち行列、アカウントの護石の端末への写し（018 pwa-offline。decisions.md Q60）
- 護石の件数の上限とページング（decisions.md Q62。一般公開の前に見直す）
- サーバーでの、マスターに依る検査と抽選テーブルとの照合（decisions.md Q61）
- 削除した護石の復元と物理削除
- 構成・武器のサーバーへの保存（011・013）と、生産護石（open-questions.md Q31）
- 本番環境へのデプロイ（009 decisions.md Q5 のとおり区間外の運用作業）
- 護石の一覧の並べ替え・絞り込み（005 と同じく扱わない）

## 契約差分
- 追加: GET /api/charms（res: 自分の削除していない護石の配列。ID の降順・ページングなし）
- 追加: POST /api/charms（req: id・payload・schemaVersion。res: 201 保存した護石。409 ID の衝突・400 構造の違反）
- 追加: PUT /api/charms/{id}（req: payload・schemaVersion・version。res: 200 保存後の護石。409 行バージョンの不一致・404 自分の行が無い・400 構造の違反）
- 追加: DELETE /api/charms/{id}（res: 204。論理削除。冪等）
- 追加: スキーマ 護石（id・payload・schemaVersion・version・createdAt・updatedAt）・護石の内容（rarity・skills・slots）・作成の要求・更新の要求（名前は区間 C で決める）
- 追加: テーブル charms(id, user_id, payload, schema_version, version, created_at, updated_at, deleted_at)。項目の確定は区間 B で行う
