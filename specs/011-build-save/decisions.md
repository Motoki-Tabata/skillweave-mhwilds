# 011 build-save の決定記録

## Q63（決定: 2026-10-28）
- 問い: 保存した構成を「開き直す」とき、何ができればよいか。構成として何を保存するか。
- 決定: 開き直しは閲覧だけとする。保存した構成の画面で、検索結果の構成のカードと同じ内容（防具・装飾品・護石・発動スキル・空きスロット・火力）を見られるようにする。検索条件（必須スキル・目的・件数・ランク）は保存せず、検索画面へ復元もしない。保存する内容は次のとおり。
  - 結果の構成: 防具 5 部位の ID（付けない部位は null）・装飾品の配置（スロットの位置と装飾品 ID）・発動スキル（スキル ID・レベル・頭打ち前の合計）・空きスロット。
  - 武器: マスターの武器は武器 ID だけ。個体差のある武器は Q64 のとおり。
  - 護石: Q64 のとおり（護石を使わない構成は null）。
  - 検索したときにオンだった発動条件の ID。火力の計算に使う。保存した構成の画面では切り替えない。
  - 構成の名前と、作成時のマスターの版（`master_version`）。
  - 発動スキルと空きスロットは、保存したときのソルバーの出力をそのまま保存して表示に使い、開くときに再計算しない。防具・装飾品・スキル・武器の名前と、防具の防御力・武器の攻撃力などの値は、開いたときのマスターと辞書から ID で引く。火力は、保存した発動スキル・発動条件と武器の攻撃力・会心率から、開いたときのマスターで計算する（007 と同じ計算）。
- 理由: 固定した構成から発動スキルを計算し直す関数を `packages/solver` は公開しておらず、再計算すると solver も触ることになって機能が大きくなる。検索条件の復元は保存する項目と画面を増やし、1〜3 日に収まりにくくなる。

## Q64（決定: 2026-10-28）
- 問い: 構成が使う護石と個体差のある武器は、ID で参照するか、内容を写すか。
- 決定: どちらも、UUID の参照と、保存した時点の内容の写しの両方を持つ。表示には写しを使い、いまの護石・武器は引かない。護石の写しは、護石の内容（レア度・スキル・スロット）とする。個体差のある武器の写しは、端末に保存した武器の内容（ベース武器 ID・表示名・攻撃力・会心率・属性・スロット・付与シリーズ／グループスキル）とする。後で護石・武器を編集・削除しても、保存した構成の表示は変わらない。
- 理由: 個体差のある武器は端末内にしか無く（013 user-weapon-save は未着手）、UUID だけでは別の端末で引けない。護石も、保存した後に編集すると保存した発動スキルと食い違う。写しを持てば構成だけで表示が完結し、012 build-share のスナップショットにもそのまま使える。UUID の参照は、機能マップの「構成は護石を UUID で参照する」と、014 guest-draft-import などの後の機能のために残す。

## Q65（決定: 2026-10-28）
- 問い: 未ログインのとき、構成の保存はどう扱うか。
- 決定: 構成の保存はログインを要する。未ログインのとき（認証状態を取得できないときを含む）は、保存できないことを示し、ログインを促す。ゲストの端末内に構成を保存する機能は作らない。保存した構成の一覧の画面も、未ログインのときはログインを促す。
- 理由: 保存・共有・複数端末利用はログイン必須とする方針（`temp/initial-design.md` §2.1）に従う。端末内の保存も作ると、010 と同じだけの作業（保存先の切り替え・残っている旨の表示）が加わる。機能マップの 014 guest-draft-import に書いた「構成」の扱いは open-questions.md の Q70 として残す。

## Q66（決定: 2026-10-28）
- 問い: 保存した構成への操作の範囲と、API の形。
- 決定: 操作は、保存（名前を付ける）・一覧・開く・名前の変更・削除とする。構成の中身は検索結果からしか作れないので、中身の上書きはしない。API は次の 4 つとし、すべてログインを要する（未ログインは 401）。状態を変える要求は CSRF トークンを要する。010 の護石の API（010 decisions.md Q59）と同じ規則に従う。
  - 一覧: ログインしているユーザーの、削除していない構成をすべて、内容を含めて返す。並びは ID の降順（新しい順）。ページングはしない。開く画面は一覧から引き、1 件を取得する API は作らない。
  - 作成: 本文に ID（クライアントで採番した UUIDv7）・名前・作成時のマスターの版・構成の内容（`payload`）・スキーマ版を受け取り、保存した構成を返す。ID が既存の行（自分の行・他のユーザーの行・削除済みの行を問わない）と衝突したら 409 で拒否する。
  - 名前の変更: 本文に名前と行バージョン（`version`）を受け取る。行バージョンが一致すれば更新して保存後の構成を返し、一致しなければ 409 で拒否する。自分の削除していない行が無ければ 404 を返す（他のユーザーの行も 404 とし、存在を漏らさない）。
  - 削除: 論理削除（`deleted_at`）にする。行バージョンは照合しない。削除済み・存在しない・他のユーザーの ID でも 204 を返し、他のユーザーの行は変えない。
  - 作成日時・更新日時・行バージョンはサーバーが管理し、クライアントが送った値は使わない。
  - 名前は、前後の空白を除いて 1〜50 文字とする。同じ名前の構成を複数保存してよい。
  - 件数の上限は設けない（010 decisions.md Q62 と同じく、一般公開の前に見直す）。
- 理由: 名前の変更は、別の端末での変更と競合しうるので、護石と同じく行バージョンで検出する。一覧に内容を含めれば、開く画面に 1 件を取得する API が要らず、API の数を護石と同じにできる。

## Q67（決定: 2026-10-28）
- 問い: 保存した構成のマスターの版が、開いたときのマスターの版と違うときの扱い。
- 決定: 保存した構成の画面に、保存したときと現在とでマスターの版が違うこと（それぞれの版）を示し、表示が保存したときと異なる場合があることを知らせる。構成の移行・再計算はしない。現在のマスターに無い ID（防具・装飾品・スキル・武器・発動条件）があっても、画面を壊さずに表示する（表示の仕方は区間 B で決める）。
- 理由: マスターは DB に置かず、ユーザーデータのマスター参照は `master_version` と照合してアプリ層で検証する（`temp/initial-design.md` §5.1）。版の更新のたびに保存した構成を移行する仕組みは、いまの規模に見合わない。

## Q68（決定: 2026-10-28）
- 問い: サーバーは、受け取った構成の内容をどこまで検査するか。
- 決定: 010 の護石（010 decisions.md Q61）と同じく、マスターに依らない構造だけを検査し、反していれば 400 で拒否する。ID は UUIDv7 の形式、名前は Q66 の長さ、スキーマ版は 1、マスターの版は空でない文字列とする。内容は、Q63・Q64 の各項目の有無と型、マスターの ID の接頭辞の形式（防具 `ar:`・装飾品 `dc:`・スキル `sk:`・武器 `wp:`・発動条件 `cd:` など）、護石の写しの構造（010 decisions.md Q61 と同じ）、配列の長さの上限を検査する。項目ごとの規則と上限の値は、区間 C で契約に書くときに決める。ID がマスターに存在するか、発動スキルが装備と合っているかは検査しない。
- 理由: サーバーはマスターを持たない（010 decisions.md Q61 と同じ）。構造と長さの検査だけで、壊れたデータや過大なデータの書き込みは防げる。

## Q69（決定: 2026-10-28）
- 問い: 別の端末での変更との競合、ログインの期限切れ、通信の失敗のとき、画面はどう振る舞うか。
- 決定: 010 の護石（010 decisions.md Q60）と同じに扱う。
  - 名前の変更が行バージョンの不一致（409）で拒否されたら、上書きせず、別の端末で変更されたことを知らせ、一覧をサーバーから読み直す。対象の構成が別の端末で削除されていた（404）ときも、その旨を知らせて読み直す。
  - 構成の API が 401 を返したら、ログインの有効期限が切れたことを知らせ、ヘッダーを未ログインの表示に戻す。
  - 一覧を取得できない（API に届かない・401 以外のエラー）ときは、読み込めなかったことと再読み込みの操作を示す。保存・名前の変更・削除の失敗はトーストで知らせ、一覧を変えない。保存の要求を後で送り直す待ち行列と、一覧の端末への写しは持たない。
- 理由: 010 と同じ規則にすると、護石と構成とで振る舞いが揃い、利用者が迷わない。
