# 011: build-save

## 目的 / ユーザーストーリー
Discord でログインしたプレイヤーとして、検索結果の気に入った構成に名前を付けて保存し、後から一覧で選んで開き直して確かめたい。PC で探した構成を、スマホなどの別の端末でも見られるようにしたい。保存はログインを要し、ゲストの端末内には構成を保存しない（`temp/initial-design.md` §2.1・decisions.md Q65）。

用語:
- 保存した構成: ログインしているユーザーがサーバーに保存した、検索結果の 1 件の構成。名前・作成時のマスターの版（`master_version`）・構成の内容を持つ（decisions.md Q63）。
- 写し: 保存した時点の護石・個体差のある武器の内容の複製。UUID の参照と一緒に持つ（decisions.md Q64）。
- 行バージョン: 保存した構成の行ごとにサーバーが持つ版（`version`）。010 の護石と同じく、別の端末での変更との競合の検出に使う。

## 受入基準（EARS記法）
- AC-1: WHILE ログインしているとき WHEN 検索結果の構成に名前を付けて保存したとき THE system SHALL クライアントで採番した UUIDv7 を ID とし、検索したときのマスターの版と、decisions.md Q63・Q64 の内容（防具・装飾品の配置・発動スキル・空きスロット・武器・護石の参照と写し・オンだった発動条件）をサーバーに保存しなければならない。
- AC-2: WHERE 未ログイン、または認証状態を取得できないとき THE system SHALL 構成を保存せず、保存にはログインが要ることを示してログインを促さなければならない。保存した構成の一覧の画面でも同じにしなければならない（decisions.md Q65）。
- AC-3: WHILE ログインしているとき THE system SHALL 保存した構成の一覧の画面に、自分の削除していない構成を新しい順に表示し、同じアカウントでログインした別の端末でも同じ一覧を表示しなければならない。
- AC-4: WHEN 保存した構成を開いたとき THE system SHALL 検索結果の構成のカードと同じ内容（防具・装飾品・護石・発動スキル・空きスロット・火力）を表示しなければならない。発動スキルと空きスロットは保存した値を使い、護石と個体差のある武器は写しを使い、名前と防具・武器の値は現在のマスターから引き、火力は保存した発動スキルと発動条件から計算しなければならない。後で護石や武器を編集・削除しても、表示を変えてはならない（decisions.md Q63・Q64）。
- AC-5: IF 開いた構成のマスターの版が現在のマスターの版と違うとき THEN システムは、両方の版を示して表示が保存したときと異なる場合があることを知らせ、構成を移行・再計算してはならない。現在のマスターに無い ID があっても画面を表示しなければならない（decisions.md Q67）。
- AC-6: WHILE ログインしているとき THE system SHALL 保存した構成の名前の変更と削除をできるようにしなければならない。名前は前後の空白を除いて 1〜50 文字とし、満たさない名前は送らず、同じ名前の構成を複数保存できるようにしなければならない（decisions.md Q66）。
- AC-7: THE system SHALL 構成の一覧・作成・名前の変更・削除の API をログインを要するものとし、一覧は自分の削除していない構成を内容とともに ID の降順で全件返し（ページングしない）、作成日時・更新日時・行バージョンをサーバーで管理しなければならない。未ログインには 401 を返し、状態を変える要求が CSRF トークンを持たないときは拒否し、他のユーザーの構成を返したり変えたりしてはならない（decisions.md Q66）。
- AC-8: IF 作成の ID が既存の行（自分・他のユーザー・削除済みを問わない）と衝突したとき THEN API は 409 で拒否し、既存の行を変えてはならない（decisions.md Q66）。
- AC-9: IF 名前の変更の行バージョンがサーバーの行と一致しないとき THEN API は 409 で拒否して上書きせず、自分の削除していない行に無いときは 404 を返さなければならない。Web は、どちらの場合も別の端末で変更・削除されたことを知らせて一覧を読み直さなければならない（decisions.md Q66・Q69）。
- AC-10: WHEN 構成を削除したとき THE system SHALL 論理削除（`deleted_at`）にし、行バージョンを照合せず、削除済み・存在しない・他のユーザーの ID でも 204 を返さなければならない。他のユーザーの行を変えてはならない（decisions.md Q66）。
- AC-11: IF 作成・名前の変更の内容がマスターに依らない構造の制約（ID は UUIDv7・名前は 1〜50 文字・スキーマ版は 1・マスターの版は空でない・内容の各項目の有無と型・マスターの ID の接頭辞の形式・護石の写しの構造・配列の長さの上限）に反するとき THEN API は 400 で拒否し、保存してはならない（decisions.md Q68）。
- AC-12: IF 構成の API が 401 を返したとき THEN Web は、ログインの有効期限が切れたことを知らせ、ヘッダーを未ログインの表示に戻さなければならない。一覧を取得できないときは、読み込めなかったことと再読み込みの操作を示し、保存・名前の変更・削除に失敗したときは、トーストで知らせて一覧を変えず、要求を後で送り直してはならない（decisions.md Q69）。
- AC-13: THE system SHALL 保存した構成を Flyway のマイグレーションで作る `builds` テーブルに保存し、その項目を `design/attributes.yaml` に確定しなければならない。
- AC-14: THE system SHALL API のテスト（Testcontainers）で、作成・一覧・名前の変更・削除、他のユーザーの構成の隔離、ID の衝突、行バージョンの不一致、構造の制約の違反、未ログインの 401、CSRF トークンの無い要求の拒否を検証しなければならない。
- AC-15: THE system SHALL Playwright（Chromium）の e2e テストで、API の応答を差し替えて、ログインしているときに検索結果の構成を保存すると一覧に出て開けること、マスターの版が違う構成を開くとその旨が出ること、名前の変更が 409 のときに知らせて読み直すこと、未ログインでは保存せずログインを促すことを検証しなければならない。

## スコープ外
- 検索条件（必須スキル・目的・件数・ランク）の保存と、検索画面への復元（decisions.md Q63）
- 構成の中身の上書き、発動スキルの再計算、マスターの版の更新に伴う構成の移行（decisions.md Q63・Q67）
- 保存した構成の画面での発動条件の切り替え
- ゲストの端末内への構成の保存と、そのサーバーへの取り込み（decisions.md Q65・014 guest-draft-import・open-questions.md Q70）
- 構成の共有（012 build-share）
- 個体差のある武器のサーバーへの保存（013 user-weapon-save）
- 構成の件数の上限・ページング・並べ替え・絞り込み（decisions.md Q66）
- サーバーでの、マスターに依る検査（ID の存在・発動スキルと装備の整合。decisions.md Q68）
- 削除した構成の復元と物理削除
- オフラインでの閲覧と、保存の要求の送り直しの待ち行列（018 pwa-offline。decisions.md Q69）
- 本番環境へのデプロイ（009 decisions.md Q5 のとおり区間外の運用作業）

## 契約差分
- 追加: GET /api/builds（res: 自分の削除していない構成の配列。内容を含む。ID の降順・ページングなし）
- 追加: POST /api/builds（req: id・name・masterVersion・payload・schemaVersion。res: 201 保存した構成。409 ID の衝突・400 構造の違反）
- 追加: PATCH /api/builds/{id}（req: name・version。res: 200 保存後の構成。409 行バージョンの不一致・404 自分の行が無い・400 名前の違反）
- 追加: DELETE /api/builds/{id}（res: 204。論理削除。冪等）
- 追加: スキーマ 構成（id・name・masterVersion・payload・schemaVersion・version・createdAt・updatedAt）・構成の内容（武器・防具・護石の参照と写し・装飾品の配置・発動スキル・空きスロット・発動条件）・作成の要求・名前の変更の要求（名前と項目ごとの規則は区間 C で決める）。護石の写しは既存のスキーマ CharmPayload を使う
- 追加: テーブル builds(id, user_id, name, master_version, payload, schema_version, version, created_at, updated_at, deleted_at)。項目の確定は区間 B で行う
