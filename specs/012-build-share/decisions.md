# 012 build-share の決定記録

## Q71（決定: 2026-10-30）
- 問い: API・DB の公開（009 decisions.md Q5 の区間外の運用作業）をいつ行うか。010・011 が済み、Q5 の「保存機能をフレンドに使ってもらう前」に当たる。公開の前に決めること・片付けることは Q83〜Q88 に分けた（独自ドメイン Q83・Web から API への経路 Q84・本番の設定 Q85・公開の前の API の変更 Q86・マネージド DB Q87・デプロイの手順 Q88）（仮: 012 build-share の区間 A の前に区間外で行う。コードの変更が要るもの（Q85・Q86）は機能 028 で先に済ませ、公開の作業はその後に行う）
- 決定: 012 は公開を待たずに進め、ローカルでデモとテストを完結させる。公開は区間外の運用作業として、012 のマージの後、共有をフレンドに使ってもらう前に行う。公開の前に決めること（Q83・Q87・Q88）は open-questions.md に残す。コードの変更が要るもの（Q85・Q86）は 028 で済んでいる。
- 理由: 共有の URL は Web が `location.origin` から組み立てるので、012 の実装は公開先のドメインや経路に依らない。公開の作業（ドメインの取得・DB・デプロイの手順）はコードの変更を伴わず、012 の区間と並べずに済む。

## Q89（決定: 2026-10-30）
- 問い: 012 build-share の共有の ID と、憲法の「ユーザーデータの ID はクライアント採番の UUIDv7」の関係。`temp/initial-design.md` §5 の `shares` は短縮 ID を持つ（仮: 行の ID は他のテーブルと同じくクライアント採番の UUIDv7 とし、URL に使う短縮 ID は別の列としてサーバーが採番する。短縮 ID の長さと文字種は 012 の区間 A で決める）
- 決定: 行の ID はクライアントで採番した UUIDv7 とする。URL に使う短縮 ID は別の列とし、サーバーが暗号論的な乱数（`SecureRandom`）で base62（`0-9`・`A-Z`・`a-z`）の 12 文字を採番する。短縮 ID は全行（取り消した共有を含む）で一意とし、一意制約に衝突したら採番し直す。取り消した共有の短縮 ID は再利用しない。
- 理由: 12 文字の base62 は約 71 ビットで、閲覧の API を総当たりして共有を探し当てることは事実上できず、URL も短く保てる。行の ID を他のテーブルと揃えると、作成の要求の送り直しの検出（ID の衝突の 409）を 011 と同じ規則で扱える。短縮 ID を再利用しないのは、取り消した URL が別の構成を指すようになるのを防ぐため。

## Q90（決定: 2026-10-30）
- 問い: 012 build-share の共有の閲覧は、未ログインで読める最初のユーザーデータの API になる。`SecurityConfig` の許可の範囲、短縮 ID を推測されない長さ、作成の件数の上限（010 decisions.md Q62 と同じく上限が無い）、共有の取り消し・有効期限の有無を決める必要がある（仮: 閲覧だけ未ログインで許し、作成と取り消しはログインした作成者だけに許す。有効期限は設けない。件数の上限は 012 の区間 A で決める）
- 決定:
  - 未ログインで許すのは、短縮 ID による共有の閲覧（GET・HEAD）だけとする。共有の作成・一覧・取り消しはログインを要し、自分の共有だけを扱える（未ログインは 401）。状態を変える要求は CSRF トークンを要する。
  - 短縮 ID の長さは Q89 のとおり。
  - 共有は保存した構成の画面から作る。自分の共有の一覧で、URL のコピーと取り消しをする（一覧の置き場は区間 B で決める）。元の構成の名前を変えても、構成を削除しても、共有の内容は変わらず、共有は残る。
  - 有効な（取り消していない）共有は 1 つの構成につき 1 つとする。有効な共有がある構成でもう一度作ると、新しく作らずに既存の共有を返す。構成の名前を変えた後に共有を作り直すときは、取り消してから作る。
  - 有効期限は設けない。取り消した共有、存在しない短縮 ID の閲覧は、どちらも同じ「見つからない」（404）とする。
- 理由: 件数は構成の数で頭打ちになるので、上限とその超過時の画面の扱いを足さずに済む（構成の件数の上限は 011 decisions.md Q66 のとおり一般公開の前に見直す）。共有の一覧を持てば、元の構成を削除した後でも共有を取り消せ、機能マップの「元を編集・削除しても内容は変わらない」を保てる。取り消しと不在を区別しないのは、取り消した共有の存在を漏らさないため。

## Q101（決定: 2026-10-30）
- 問い: 共有のスナップショットに何を入れ、どこから作るか。共有の API の形をどうするか。
- 決定:
  - 共有の作成は、本文に共有の ID（クライアントで採番した UUIDv7）と元の構成の ID だけを受け取り、サーバーが自分の削除していない構成の行から、名前・作成時のマスターの版・構成の内容（`payload`）・スキーマ版を写す。クライアントから構成の内容を受け取らない。元の構成が自分の削除していない行に無ければ 404（他のユーザーの構成も 404 とし、存在を漏らさない）。共有の ID が既存の行と衝突したら 409。有効な共有が既にあれば、その共有を返す（Q90）。
  - 構成の内容は 011 の保存した構成の `payload` をそのまま写す（護石・個体差のある武器の写しと、その UUID の参照を含む）。作成者の Discord の名前・アバターなど、ユーザーの情報は共有にも閲覧の応答にも含めない。
  - 閲覧の API は、管理の API（一覧・作成・取り消し）と別のパスに置き、`SecurityConfig` ではそのパスの GET・HEAD だけを未ログインに許す。応答は、名前・マスターの版・構成の内容・スキーマ版・共有の作成日時とし、共有の行の ID と元の構成の ID は返さない。
  - 自分の共有の一覧は、取り消していない共有を ID の降順で全件返す（ページングしない）。各共有は、ID・短縮 ID・元の構成の ID・名前・作成日時を持つ。
  - 取り消しは論理削除（`deleted_at`）とし、取り消し済み・存在しない・他のユーザーの ID でも 204 を返し、他のユーザーの行は変えない（011 decisions.md Q66 の削除と同じ）。
- 理由: 011 の構成は内容を上書きできない（011 decisions.md Q66）ので、サーバーの行から写せば、保存したときのソルバーの出力をそのまま共有でき、構造の検査を共有の側で繰り返さずに済む。payload から UUID の参照を取り除くには、サーバーが payload の中身を書き換える処理を持つ必要があり、参照の UUID だけでは他人の護石・武器を読めないので、そのまま写す。共有の行の ID と元の構成の ID を閲覧の応答から外すのは、管理の操作の対象を受け手に渡さないため。

## Q102（決定: 2026-10-30）
- 問い: 共有の URL を開いた受け手の画面で、何を見せるか。
- 決定: 共有の URL（短縮 ID を含む Web のパス）は、ログインしていなくても開ける画面とする。保存した構成の画面（011）と同じ内容（防具・装飾品・護石・発動スキル・空きスロット・火力・オンだった発動条件）と構成の名前を、011 decisions.md Q63・Q64 と同じ規則で表示する。マスターの版が現在の版と違うときは、011 decisions.md Q67 と同じく、両方の版を示して表示が異なる場合があることを知らせる。作成者の情報は示さない。取り消し済み・存在しない共有は「見つからない」旨を、取得に失敗したときは読み込めなかったことと再読み込みの操作を示す。受け手が共有の構成を自分の構成として保存する操作は作らない。
- 理由: 保存した構成の画面の表示（`savedBuildView` と構成のカード）をそのまま使えば、受け手と作成者とで同じ表示になり、計算の規則も揃う。自分の構成として保存する操作は、作成の API に共有の構成を受け取る経路を足すことになり、1〜3 日に収まりにくくなる。
