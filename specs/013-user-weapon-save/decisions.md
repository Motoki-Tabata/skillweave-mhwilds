# 013 user-weapon-save の決定記録

## Q72（決定: 2026-10-30）
- 問い: 010・011 の API の入力の検査で、ゲート D-1 で持ち越した点をどこで直すか。(1) 文字列の項目（構成名・武器名・護石の文字列項目）に JSON の数値・真偽を送ると文字列に変換されて 201 になる、(2) `CustomWeaponPayload.element` が null のとき省略扱いで 201 になる（契約は null 不可）、(3) 名前・武器名に U+0000 が通る（PostgreSQL は NUL を保存できず、DB のエラーになりうる。実測していない）（011 handoff.md「PR 本文に必須の記載事項」）。
- 決定: 013 で、護石・保存した構成・個体差のある武器のすべての API に効く検査としてまとめて直す。どれも 400 で拒否し、保存しない。
  - (1) 文字列の項目に JSON の文字列以外（数値・真偽など）を送った要求は拒否する。
  - (2) 省略できる項目（`element` など）は省略だけを許し、明示の null は拒否する（契約どおり）。構成の武器の写しと、個体差のある武器の API の内容の両方に効かせる。
  - (3) 文字列の項目に U+0000 を含む要求は、取り除かずに拒否する。いまの挙動（DB のエラーになるか）は、区間 C で先に実測する。
- 理由: 3 つとも、契約と API の実際の受け付けが食い違っている。API ごとに直すと検査の厳しさが API によって違う状態が続くので、武器の API を足す 013 で、全 API に一度に効かせる。U+0000 を取り除いて保存すると送った値と保存される値が変わり、ほかの構造の違反（400）と性質が違ってしまう。

## Q98（決定: 2026-10-30）
- 問い: ログインしているとき、個体差のある武器の画面と検索の武器の選択肢は、どの武器を使うか。端末内（IndexedDB）の武器をどう扱うか。
- 決定: 010 の護石（010 decisions.md Q58）と同じに扱う。ログインしているときは、武器の画面も検索の武器の選択肢も、サーバーに保存した武器（アカウントの武器）だけを使う。端末内の武器は消さず、サーバーへ送らず、ログインしている間は表示しない。ログアウトすると、ふたたび端末内の武器を表示する。画面には、いまの保存先（この端末かアカウントか）を示し、ログインしている間に端末内に武器が残っていればその旨を示す（文言と置き場は区間 B で決める）。未ログインのときと、認証状態を取得できないときは、008 のとおり端末内の武器を使う。
- 理由: 端末内の武器のサーバーへの取り込みは 014 guest-draft-import で一方向・一回きりで行う（`temp/initial-design.md` §2.1）。両方を並べると、014 で取り込んだ後に同じ武器が二重に並ぶおそれがあり、護石と扱いが食い違う。025 で保存先の状態機械を共有部品にしてあり（025 decisions.md Q73）、武器のストアに API を渡すだけで護石と同じ振る舞いになる。

## Q99（決定: 2026-10-30）
- 問い: 個体差のある武器を保存する API の形と、サーバーが受け持つ項目・検査の範囲。別の端末での変更との競合、ログインの期限切れ、通信の失敗のとき、画面はどう振る舞うか。
- 決定: 010 の護石の API（010 decisions.md Q59・Q60・Q61・Q62）と同じ規則に従う。
  - API は一覧・作成・更新・削除の 4 つとし、すべてログインを要する（未ログインは 401）。状態を変える要求は CSRF トークンを要する。一覧は自分の削除していない武器を ID の降順で全件返す（ページングしない）。作成は ID（クライアントで採番した UUIDv7）・内容・スキーマ版を受け取り、ID が既存の行（自分・他のユーザー・削除済みを問わない）と衝突したら 409。更新は内容・スキーマ版・行バージョンを受け取り、行バージョンの不一致は 409、自分の削除していない行が無ければ 404。削除は論理削除で行バージョンを照合せず、常に 204。作成日時・更新日時・行バージョンはサーバーが管理する。件数の上限は設けない。
  - 武器の内容の形は、構成の武器の写しの契約 `CustomWeaponPayload`（011）を使い、Web の端末の武器（`WeaponPayload`）と同じ形にする。応答は端末の武器と同じ形に行バージョンを加えて返す。
  - サーバーはマスターに依らない構造だけを検査する（`CustomWeaponPayload` の制約と Q72）。基の武器・付与スキルがマスターにあるか、種別が合っているかの検査は、008 のとおり Web で行う。
  - 409・404・401・一覧の取得の失敗・保存と削除の失敗の画面の扱いは、010 decisions.md Q60 と同じにする（トーストの文言は護石の文言の名詞を武器に替えたものを基にし、区間 B で確定する）。
- 理由: 護石と同じ規則にすると、025 で共有部品にした保存先の状態機械（`useSavedItems`）と API の型（`SavedItemsApi`）をそのまま使え、利用者にとっても護石と武器で振る舞いが揃う。構成の写しと同じ形にすれば、武器の内容の契約と検査を 1 つで持てる。

## Q100（決定: 2026-10-30）
- 問い: 検索条件で選んでいる個体差のある武器が、保存先の切り替え（ログイン・ログアウト・401）や、409・404 のあとの一覧の読み直しで一覧から消えたとき、検索条件の武器の選択をどう扱うか。
- 決定: 消えた理由を問わず、検索条件の武器の選択を外す。008 の「検索条件で選んでいる武器を削除したら選択を外す」と同じ扱いにする。
- 理由: いまは選択だけが残り、検索しようとしたときに武器のエラーが出る。ログアウトやほかの端末での削除は利用者が武器を選び直す前提の出来事なので、削除と同じく選択を外すほうが分かりやすい。
