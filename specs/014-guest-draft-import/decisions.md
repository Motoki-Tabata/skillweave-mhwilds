# 014 guest-draft-import の決定記録

## Q70（決定: 2026-10-31）
- 問い: 014 guest-draft-import の取り込みの対象に「構成」を残すか。011 build-save はゲストの端末内に構成を保存しない（011 decisions.md Q65）ので、取り込むゲストの構成が無い（仮: 014 の区間 A で、機能マップの 014 の「1行の価値」から「構成」を外すか、ゲストの構成の端末内の保存を別の機能として足すかを決める）
- 決定: 構成を外す。取り込みの対象は、端末内（IndexedDB）に保存している護石（005）と個体差のある武器（008）の2つだけとする。機能マップの 014 の「1行の価値」から「構成」を外し、依存から 011 を外す。ゲストの構成を端末内に保存する機能は足さない。
- 理由: 端末内に保存しているユーザーデータは護石と武器だけで（`apps/web/src/main/lib/storage/database.ts` のストアは `charms`・`weapons`）、取り込む構成が無い。端末内の構成の保存を足すと、010 と同じだけの作業（保存先の切り替え・残っている旨の表示）が加わり、011 decisions.md Q65 の判断を覆すことになる。

## Q103（決定: 2026-10-31）
- 問い: 取り込みはどう始めるか。ログインを判定した時点で自動で送るか、利用者の操作で始めるか。
- 決定: 利用者の操作で始める。ログインしている間に護石・武器の画面に出す「この端末に N 件残っています」の帯（010 decisions.md Q58・013 decisions.md Q98）に、アカウントへ取り込む操作を置く。護石の画面では護石を、武器の画面では武器を取り込む（画面ごとに別々に取り込む）。操作の後に、取り込む件数と、取り込んだものを端末から消すことを示して確認を取り、承認されてから送る。端末内に残っている件数が 0 のときは、帯も操作も出さない。文言・確認の形・置き場は区間 B で決める。
- 理由: 自動で送ると、共用の端末で別の Discord アカウントにログインしたときに、そのアカウントへ他人の下書きを取り込んでしまい、一方向のため取り消せない。残っている旨の帯は 010・013 で既に出しているので、その場に操作を足すのが最も小さい。

## Q104（決定: 2026-10-31）
- 問い: 取り込みが済んだ端末内の護石・武器をどうするか。「一回きり」をどう保つか。
- 決定: 端末から消す（移動）。サーバーが受け付けた1件ごとに、その1件を端末から消す。取り込みを始める時点で、アカウントの一覧に同じ ID が既にあるもの（前回の取り込みでサーバーには入ったが端末から消せなかったもの）は送らずに端末から消し、取り込んだものとして数える。取り込みでは ID を振り直さず、端末の ID（UUIDv7）のままサーバーへ送る。取り込んだ後は、ログアウトすると端末の一覧は取り込まなかった分だけになる。
- 理由: 端末から消せば、同じものを二度送ることがデータの状態として起きず、取り込み済みの印とその表示の扱いを持たずに済む。ID を変えないことは憲法（ユーザーデータの ID はクライアント採番の UUIDv7）と `temp/initial-design.md` §2.1 の前提であり、同じ ID がアカウントにあるかで取り込み済みを判定できる。

## Q105（決定: 2026-10-31）
- 問い: サーバーへどう送るか。1件ごとの失敗をどう扱うか。
- 決定:
  - 010 の護石・013 の武器の作成 API を、1件ずつ順に呼ぶ。契約と API は変えない。送る内容とスキーマ版は端末のものをそのまま使い、作成日時・更新日時・行バージョンはサーバーが付ける（010 decisions.md Q59。端末の作成日時・更新日時は引き継がない）。マスターとの照合（005・008 の検査）は取り込みでは行わず、端末にあるものをそのまま送る。
  - その1件だけの拒否（400: 構造の検査に反する、409: ID が他のユーザーの行・削除済みの行と衝突する）は、その1件を端末に残し、取り込めなかったものとして数えて、次の1件へ進む。
  - 401 は、そこで止め、010 decisions.md Q60 の期限切れの扱い（知らせて未ログインの表示に戻し、端末の一覧に切り替える）に従う。
  - それ以外の失敗（API に届かない・5xx など）は、そこで止める。送っていない分は端末に残る。
  - 終わったら（止めたときも）、取り込んだ件数と、取り込めなかった・送らなかった件数を知らせ、アカウントの一覧と端末内の件数を読み直す。端末に残った分は、帯の操作から取り込み直せる。文言は区間 B で決める。
- 理由: ゲストが手入力する件数は多くても数十件と見込まれ、1件ずつ送っても要求数は問題にならない。既存の API を使えば契約・API の変更が要らず、保存先の状態機械（025 の `useSavedItems`）の作成の扱いに揃えられる。1件だけの拒否は送り直しても通らないので飛ばし、通信の失敗や期限切れは送り続けても通らないので止める。

## Q106（決定: 2026-10-31）
- 問い: 護石の件数の上限とページング（010 decisions.md Q62「一般公開（014 guest-draft-import）の前に見直す」）を 014 でどうするか。
- 決定: 014 では上限もページングも設けない（010・011・013 のまま）。一般公開の前に、ユーザーデータの API 全体で上限・ページング・要求の頻度の制限を設けるかを決めることを、open-questions.md の Q107 として残す。
- 理由: 取り込む件数は端末内にある件数（ゲストの手入力の件数）を超えず、取り込みによって1ユーザーの件数が手入力より速く増えることは無い。作成 API を繰り返し呼べば件数がいくらでも増えるのは 014 に依らない一般公開の課題であり、護石だけでなく武器・構成・共有にも同じく当てはまるので、014 に含めず一般公開の前提として扱う。
