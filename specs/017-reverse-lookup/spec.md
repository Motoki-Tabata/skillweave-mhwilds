# 017: reverse-lookup

## 目的 / ユーザーストーリー
ゲストまたはログインユーザーとして、検索画面の条件（武器・必須スキル・防具の固定と除外・装飾品の除外）で「どんな鑑定護石があれば組めるか」を、抽選テーブル（036 で入れた `appraisedCharm`）から逆引きしたい。手持ちの護石で組めない構成を狙うときに、どのレア度の、どのスキルとスロットの護石を厳選すればよいかが分かるようにするためである。

## 受入基準（EARS記法）
- AC-1: WHEN ユーザーが検索画面で逆引きを実行したとき、THE system SHALL 検索画面の条件（武器・必須スキル・防具の固定と除外・装飾品の除外）をそのまま使い、護石だけを抽選テーブルから出うる仮想の護石に置き換えて解かなければならない。登録した鑑定護石と生産護石は使わず、目的関数は使わずに組めるかだけを見る（decisions.md Q167）。
- AC-2: THE system SHALL 仮想の護石を、抽選テーブルのどれか1つのパターンに収まるもの（スキルの i 番目がそのパターンの i 番目の群に同じスキルとレベルで含まれ、スロットの並びがそのパターンの `slotPatterns` のどれかと一致する）に限らなければならない。
- AC-3: THE system SHALL 仮想の護石に同じスキルを2つ持たせてはならない（036 decisions.md Q174）。
- AC-4: WHEN 逆引きの候補が見つかったとき、THE system SHALL 候補ごとに、護石のレア度・スキルとレベル・スロットの並びと、その護石を使ったときの構成（防具・装飾品・発動スキル）を示さなければならない。構成に効かないスキルの枠は「任意」と示す（Q167）。
- AC-5: THE system SHALL 互いに異なる護石（「任意」の枠を除いたスキルとレベル、スロットの並びの組）を最大10件示し、要るスキルの数が少ない順、次に要るスキルのレベルの合計が低い順、次にレア度が低い順に並べなければならない（Q169）。
- AC-6: THE system SHALL 先に示した候補より要求が厳しいだけの候補（先の候補の要るスキルを同じか高いレベルですべて含み、スロットの並びが同じもの）を示してはならない。
- AC-7: IF どの仮想の護石でも組めないとき、THEN システムは、抽選テーブルのどの護石でも条件を満たせない旨を示さなければならない。
- AC-8: WHERE 抽選テーブルが無いレア度があるとき、THE system SHALL そのレア度を仮想の護石の候補に含めてはならない。どのレア度のテーブルも無いマスターでは、逆引きを実行させず、抽選テーブルが未整備である旨を示さなければならない（Q167）。
- AC-9: THE system SHALL 逆引きをブラウザ内の Worker で実行し、実行中に取り消せて、時間の上限に達したときはそれまでに見つかった候補を、打ち切った旨とともに示さなければならない（通常の検索と同じ扱い）。
- AC-10: THE system SHALL 仮想の護石の選択を `packages/solver` の ILP の変数として持ち、1回の求解で護石と構成を同時に決めなければならない。`packages/solver` は API の型と DOM に依存しない（Q168）。
- AC-11: WHEN 実データ（現行のマスター）の測定用の条件で逆引きを実行したとき、THE system SHALL 1件目の候補までの時間を、検索の基準（3秒）以内に収めなければならない。
- AC-12: THE system SHALL 逆引きを足しても、通常の検索（登録した護石・生産護石を候補にする検索）の要求・結果・挙動を変えてはならない。

## スコープ外
- 抽選の確率（重み）の表示と、確率による並べ替え（Q169。データが無い）。
- 逆引きの候補を保存する・共有する・護石一覧へ登録する操作。
- 生産護石を「作れば組める」候補として示すこと。
- 目的関数（期待値・防御力・空きスロットの最大化）で候補を並べること（Q167）。
- 手持ちの護石と組み合わせた逆引き（手持ちの護石の性能を上回る候補だけに絞るなど）。
- 抽選テーブルの中身の修正（036 の担当）。
- 逆引きの結果を `/builds` の構成として保存すること。

## 契約差分
- なし（API を持たない。ソルバーとマスターの JSON だけを使う）
