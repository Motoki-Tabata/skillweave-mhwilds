## 決定事項

### 求解の方式の試作と決定（decisions.md Q41）
- D1: 求解の方式は、区間 D の最初に solver-agent が試作し、実データで測ってから決める（Q41。3 秒に届く方式は未確認のため、委譲の前には決めない）。試作の候補は次のとおり。単独と組み合わせの両方を測る。どの候補も 006 Q36 の厳密さ（期待値の最大から順・同点は防具用、次に武器用の空き Lv の合計）を変えてはならない。
  - (a) HiGHS の設定: `presolve` を `off`、`mip_allow_restart` を `false`、およびその組み合わせ（区間 A の切り分けで、1回の求解が約 4.2 秒から 1.1〜1.6 秒になった）。
  - (b) 支配される防具・装飾品を候補から外す（定義は D5。区間 A の切り分けで、各部位の防具の候補が約半分になった）。
  - (c) 2件目以降の上限の行: 直前の件の期待値を E_prev として、θ ≤ E_prev + ε（ε は `DAMAGE_EPSILON`）を足す。除外の行が増えるだけなので次の件の期待値は E_prev を超えず、厳密さは変わらない。LP 緩和の値（区間 A で整数解より約 50% 大きい）を締める。
  - (d) 定式化の強化: 積 A·g·p_b の線形化の big-M（現行は A の上界 `attackUpper`）を締める。例: 攻撃力を会心倍率の候補ごとに分ける（A = Σ_j A_j、A_j ≤ 上界·g_j とし、w(j,b) ≤ A_j、w(j,b) ≤ 上界·p_b にする）。
  - (e) 2段目の扱い: 1段目の解を `Model.setSolution` で2段目の初期解に渡す、または `Model.passLinearObjectives` の優先度つきの多目的で1回にまとめる（後者は、同点の順が ε の扱いを含めて現行の2段と一致することを確かめる）。
  - (f) 2件目以降に、直前の件の解（除外の行で不可能になる）ではなく、1段目の過程で得た次善の解を初期解に渡す等、試作の中で見つけた工夫。採るときは報告に厳密さが変わらない理由を書く。
- D2: 試作は、`packages/solver/src/main` を変えずに、測定専用のファイル `packages/solver/src/test/damagePrototype.measure.ts`（CI では実行しない。`describe` の名前は `期待値の方式の試作` とし、`expectedDamage` の語を含めない。006 の測定の `-t "expectedDamage"` で同時に走らないようにするため。実行の手順は報告に書く）に書く。`buildModel`・`extendWithDamage` 等の既存の関数を読み、候補の (b) はマスターの防具・装飾品を絞った写しを渡し、(d) は `extendWithDamage` の写しを試作のファイルの中で書き換える。条件は 006 の測定と同じ（D8 の条件）。報告には、候補（と組み合わせ）ごと・ケースごとの合計時間の最大と1件目までの時間の最大、求解の回数、1件目の期待値が現行の実装と `DAMAGE_EPSILON` 以内で一致するか、10件の期待値の列が現行と一致するか（(b) は 1件目だけ一致すればよい。Q41）を表で載せる。1つの候補の測定が 1 ケースで 60 秒を超えるときは打ち切ってよい（報告に打ち切ったことを書く）。試作のファイルはコミットし、本実装（T4）で削除する。
- D3: 方式の決定は、T2 の報告を受けてメインがユーザーに確認し（設計判断のため）、確定した方式を本 plan.md の D11 に、試作の結果の要約を decisions.md Q41 の「判断材料」に追記する（T3）。判断の順は次のとおり: 合計時間の最大が 3 秒以下の方式があれば、そのうち変更が小さいもの。無ければ、1件目までの時間の最大が最も小さい方式を採り、D6 の進捗の通知を T4 に含める。1件目までも 3 秒を超えるなら、最も速い方式を採ったうえで、T5 の後に T7 で起票する。支配の除外（候補 (b)）は、採る方式に含まれるときだけ実装する（受入基準 2 は WHERE の条件つき）。

### 本実装（受入基準 1〜6・9）
- D4: 2段目の求解が解なしのときは、例外にせず、1段目の解の構成をその件として返す（受入基準 5。006 のゲート D-1 の決定）。`score` は1段目の構成から計算し直した期待値（006 D15 と同じ）。除外の行は1段目の解の防具と護石の組で足す。2段目が時間切れのときは、現行どおりその件を返さずに状態 `timeout` で終える。D11 の方式が2段目を持たないときは、本決定は対象外とし、受入基準 5 は該当なしとして報告する。
- D5: 支配される候補（D11 で採るときだけ。受入基準 2）。対象は目的関数が `expectedDamage` のときの防具と装飾品だけで、護石・固定した部位・他の目的関数の候補は変えない（受入基準 3）。固定・除外（`fixedArmor`・`excludedArmorIds`）を適用した後の候補の中で判定する。
  - 関係するスキル: 必須スキル（通常・シリーズ／グループ）と、期待値の対象のスキル（`damageTargets`）。
  - 防具 X が防具 Y に支配される: 同じ部位で、関係する通常のスキルのレベルがすべて X ≤ Y、関係するシリーズ／グループの所属が X ⊆ Y、スロットが種別（`weapon`・`armor`）ごとに Lv を降順に並べて要素ごとに X ≤ Y（数が足りない側は 0 とみなす）。
  - 装飾品 X が装飾品 Y に支配される: 同じ種別で、関係するスキルのレベルがすべて X ≤ Y、装飾品の Lv が X ≥ Y。
  - 互いに支配し合う（関係する属性がすべて等しい）候補は、マスターの並びで最初のものだけを残す（決定的にするため）。
- D6: 進捗の通知に構成を載せる（D3 で必要と判断したとき、または T5 で合計時間の最大が 3 秒を超えたときだけ。受入基準 9）。形は `SolveOptions.onProgress?: (found: number, build: SolvedBuild) => void`（既存の `(found) => …` の呼び出し側はそのまま型が通る）と、Worker の `progress` のメッセージへの `build: SolvedBuild` の追加。目的関数を問わず同じ形で載せる（列挙の共通の経路のため）。`apps/web` は変えない（逐次表示は 007）。
- D7: テスト（`packages/solver/src/test/**`）。
  - 受入基準 1・3: 006 の既存のテスト（`solveBuilds.damage.spec.ts`・`solveBuilds.spec.ts`）を変えずに通す。D11 で同点の順の扱いを変えるときは、同点の順のテストが通ることを確かめる。
  - 受入基準 2・4: 支配の除外を採るときは、手作りの小さなマスター（支配される防具・装飾品と、互いに等しい候補を含む）で、D5 の候補の定義で総当たりした列（`support/bruteForce.ts`）と、1件目の期待値が除外しない総当たりの最大と一致すること、2件目以降が除外した候補での総当たりの最大と一致することを確かめる。支配の判定の関数の単体テストも書く。全構成の独立の検算と降順（006 の `verifyBuild`）は全件に掛ける。
  - 受入基準 5: HiGHS の `Model.run` を包んで2段目だけ解なしを返す差し替え（`solveBuilds.measure.ts` の `instrument` と同じ包み方）で、例外にならず1段目の構成が返ることを確かめる。
  - 受入基準 6: `expectedDamage` で、時計を進める `now` による時間切れ（それまでの構成と状態 `timeout`）と、キャンセル（`SolveCancelledError`）を確かめる。D6 を入れるときは、`onProgress` の2番目の引数が返す構成と同じ並びで渡ることも確かめる。
- D8: 測定ハーネス（`src/test/solveBuilds.measure.ts`）の `expectedDamage` のケースに、1件目までの時間（開始から最初の `onProgress` の呼び出しまで。HiGHS の初期化は含めない）を足し、ケースごと・回ごとの合計時間と1件目までの時間、全ケース・全回のそれぞれの最大、3 秒に対する合否（合計時間の基準と、未達のときの1件目までの基準の両方）を出力する（受入基準 7）。条件は 006 と同じ（実データ・条件をすべて有効・マスターの先頭の武器・護石なし・`maxResults` 10・必須スキル 3／6／10 個 × 解あり／解なし・各 3 回・`timeoutMs` 60 秒・Node）。CI では実行しない（`ciTiming.spec.ts` の検査のまま）。
- D9: 実データのテスト（`src/test/solveBuilds.real.spec.ts`）のすべての `solveBuilds` の要求に `timeoutMs` を明示し、状態が `timeout` でないこと（解ありは `optimal`、解なしは `infeasible`）を検算の前に検査する（受入基準 10）。`timeoutMs` は vitest のそのテストの時間の上限より短くする。
