# 021 crafted-charm の決定記録

## Q31（決定: 2026-10-28）
- 問い（`open-questions.md` からの移設）: 生産護石（マスターの `charms`）をソルバーの候補にする方式。`SolverCharm.id` は `Uuid` 型で、マスターの `CharmId`（`ch:...`）を渡すには `packages/solver` の型の変更が要る。防具と同じく「すべて持っている」とみなすか、所持を入力させるかも未定（仮: 機能マップに 021 crafted-charm として追加した。方式は 021 の区間 A で決める）
- 決定（所持）: 防具と同じく、生産護石はすべて持っているとみなす。系統ごとの所持の入力と保存はしない。検索画面の護石の節に「生産護石を候補に含める」の切り替えを置き、既定はオンとする。オフのときは、登録した鑑定護石だけを候補にする（005 までと同じ）。切り替えの見た目・位置と、状態を保持するかは区間 B で決める。
- 決定（型）: `packages/solver` の `SolverCharm.id` と `SolvedBuild.charmId` の型を `Uuid | CharmId` に広げるだけにする。ソルバーは護石の ID を読まずに出力へ写すだけなので、求解の処理は変えない。鑑定護石か生産護石かの区別は `apps/web` 側で、ID が `CharmId` の形（接頭辞 `ch:`）かどうかで行う。
- 決定（表示）: 結果の構成のカードで、生産護石を使った構成には護石の名前（辞書の名前。例: 「耳栓の護石Ⅲ」）を出す。レア度・スキル・スロットの表示は鑑定護石と同じにする。
- 理由: 生産護石は素材さえあれば作れるので、防具と同じ扱いにすると入力の手間が無い。所持の入力は画面と端末内の保存が増え、M に収まりにくい。生産護石を使いたくない人のために、まとめての切り替えだけを置く。型を判別共用体（`kind`）にする案は、ソルバーが ID を読まないのに、ソルバーのテストと `apps/web` の変更を増やすので採らない。

## Q77（決定: 2026-10-28）
- 問い: ソルバーへ渡す生産護石を絞るか。マスターの生産護石は 60 系統・183 件（ランクⅠ〜Ⅴ）ある。
- 決定: 系統（ID の `ch:<gameId>:<ランク>` の `gameId`）ごとに、最上位ランクの1件だけを候補として渡す。結果の構成に出る生産護石は、その系統の最上位ランクになる。
- 理由: マスター 2026.10.4 で、どの系統でも上位ランクが下位ランクのスキル（同じスキルで同じ以上のレベル）とスロットを包含していることを確かめた（例外なし）。全所持とみなすなら、下位ランクを渡しても良い構成は増えない。渡すと ILP の列が増え、ランク違いだけの構成が結果に並びうる。
- 絞り込みは `apps/web` のアダプタで行い、包含の関係が崩れたマスターに備えて、包含を前提にした処理であることをテストで示す。包含の検査をパイプラインに足すかは区間 C で決める。
- 候補の列は最大 60 件増える。区間 D で、`packages/solver` の測定（`--mode measure`）で生産護石ありの所要時間を測って記録する。基準（Q50 など）を超えても 021 では高速化しない（024 worker-solve-perf で扱う）。

## Q78（決定: 2026-10-28）
- 問い: 生産護石を使った構成を保存できるようにするか。構成の保存の契約 `BuildCharm.id` は `format: uuid` で、API（`BuildCharm` の `UUID id`）も UUID だけを受け付けるため、`CharmId` を保存するには契約と API の変更が要る。
- 決定: 021 では保存できないようにする。生産護石を使った構成のカードには保存の操作を出さず、保存できない理由を示す。鑑定護石を使った構成と護石なしの構成は、これまでどおり保存できる。生産護石を使った構成の保存（`BuildCharm` の契約・API・`apps/web` の保存と表示）は、機能マップに 027 crafted-charm-build-save として追加した。`BuildCharm` の形（`kind` で判別するかなど）は 027 の区間 A で決める。
- 理由: 保存まで 021 に含めると、触る領域が solver・web・contracts・api の 4 つになり、上限の 3 つを超える。ソルバーの型の変更を別の機能に分ける案は、型の変更だけでは画面で確かめられない機能になるので採らない。
