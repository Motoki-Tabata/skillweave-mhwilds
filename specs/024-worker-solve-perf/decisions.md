# 024 worker-solve-perf の決定記録

## Q50（決定: 2026-10-29）
- 問い（`open-questions.md` から移設）: ブラウザの Worker 上の `expectedDamage` の1件目までの時間が 3 秒を超えた（最大 3353.6 ms。Node の 2609.6 ms より約 0.74 秒遅い。記録は `design/tech-stack.md`「ブラウザの Worker 上の expectedDamage の測定（007 damage-ui・2026-10-26）」）。また解ありの 3 ケースは合計時間が画面の上限 30 秒に近く、k=3 は 3 回とも打ち切られた（8 件）。求解の高速化（1件目の求解の短縮・候補の絞り込みなど）で 3 秒以内に収めるか、基準を見直すか（仮: 機能マップに 024 worker-solve-perf として追加した。高速化か基準の見直しかは 024 の区間 A で決める。逐次表示（007）で1件目は 3.4 秒後に画面に出るので、使えないほどではない）
- 決定:
  - 厳密さは 006 の Q36 のまま保ち（期待値の最大から順に返す。近似で候補を絞ってから並べ替える方式は採らない）、`packages/solver` の高速化を区間 C で試作して実データで測り、採る方式を決める。試作の候補は、定式化の作り直し（会心倍率の候補ごとに分けて解くなど）・HiGHS の設定・候補の絞り込み（019 decisions.md Q41 の支配される候補の除外。生産護石どうしの支配を含む）とする。
  - 合格基準は、画面（ブラウザの Worker。`apps/web` の測定 `pnpm --filter @swv/web run measure`）で、007 と同じ 6 ケース・各 3 回を、生産護石を候補に含める（既定のオン）とオフの両方で測り、全ケース・全回の1件目までの時間の最大が 3 秒以下であること。合計時間は基準にしない。CI では測らない。結果は `design/tech-stack.md` に記録する。
  - 試作して 3 秒に届かないときは、届いた値を記録し、基準を「画面での1件目までの時間の最大が 5 秒以下」に読み替える（逐次表示と検索中の表示があることが前提）。5 秒も超えたときは、次の対策を新しい Q として起票し、024 はその記録をもって閉じてよい。
  - 目的が `defense` の検索も、画面で生産護石ありとなしの両方を測って記録する。基準（004 の画面の合計時間 3 秒以下）を超えたら新しい Q を起票し、024 では `defense` を高速化しない。
- 判断材料（2026-10-29。`design/tech-stack.md` の既存の記録から）:
  - 画面の測定（007）は生産護石をオフにして測っている（`apps/web/e2e/measure/damage-ui.measure.ts` がチェックを外す）。021 以降の既定は生産護石オンで、その条件の画面の時間は未測定。
  - Node で生産護石ありにすると、`expectedDamage` の1件目までの最大が 4522.8 ms になる（021 の測定）。画面は Node より約 0.7 秒遅いので、既定の操作では1件目が 5 秒前後と見込まれる。
  - 019 で HiGHS の設定（`presolve` off・`mip_allow_restart` false）と2段の1回化は採用済み。支配される候補の除外は、1件目を 0.1〜0.3 秒縮めるだけだった（019 decisions.md Q41 の試作の結果）。LP 緩和の値は整数解より約 50% 大きく、緩和が弱い。
  - `defense` は Node・件数 30 で最大 4.5 秒だが、画面の基準（件数 10）では 004 で合格している。生産護石ありの画面の時間は未測定。
- 採らなかった案: 基準の見直しだけ（求解を変えない）は、既定の生産護石オンで1件目が 5 秒前後になる見込みを放置するため採らない。近似を許す案は、1件目が真の最大である保証を失うため採らない（019 Q41 と同じ）。3 秒を必達にする案は、届くかが試作するまで分からず、日数の見込みが立たないため採らない。
