## 決定事項

### 求解の方式の試作と決定（decisions.md Q50）
- D1: 求解の方式は、区間 D で solver-agent が試作し、実データで測ってから決める（Q50。3 秒に届く方式は未確認のため、委譲の前には決めない。019 の Q41 と同じ進め方）。試作の候補は次のとおり。単独と組み合わせの両方を測る。どの候補も 006 Q36 の厳密さ（期待値の最大から順・同点は防具用、次に武器用の空き Lv の合計）を変えてはならない。019 で採らなかった候補（会心倍率の big-M を締めるだけの定式化の強化・2段目への初期解の受け渡し）は、そのままの形では繰り返さない。
  - (a) 会心倍率の候補ごとに分けて解く: 会心倍率の候補 g_j（現行は 1.25 と `crit_mul` の値の 6 個）を1つずつ固定した部分問題を解き、部分問題の間の最大を1件目にする。部分問題 j の期待値は、構成の実際の会心倍率が v_j 以上のとき v_j で数えた値で、真の値以下になり、真の会心倍率の部分問題で真の値に一致するので、最大は変わらない。部分問題は、θ だけを目的にした LP 緩和の上界の大きい順に解き、それまでの最良の期待値から `DAMAGE_EPSILON` を引いた値が次の部分問題の上界より大きくなったら残りを解かない（同点の候補を落とさないよう、ε の分だけ余分に解く）。2件目以降は、除外の行をすべての部分問題に足して同じ手順を繰り返す。部分問題の最適解の防具と護石の組が除かれていなければ、その最適解は除外の後も最適なので、解き直さずに再利用してよい。固定の仕方は、同じモデルで g の列の上下限を変える方法（`changeColBounds`）と、部分問題ごとに g と積の列を持たないモデルを作る方法の両方を試す。部分問題をまたいだ同点の順（ε 以内の期待値で空き Lv の重みが大きいものを選ぶ）を現行と同じにする手順を報告に書く。
  - (b) 支配される候補を外す（定義は D4。生産護石どうしの支配を含む）。単独と、(a) との組み合わせを測る。
  - (c) 下限の受け渡し: (a) の部分問題や2件目以降の求解に、それまでに分かっている期待値の下限を渡して探索を絞る（θ ≥ 下限 − ε の行、HiGHS の `objective_bound`、`Model.setSolution` による初期解のいずれか）。1件目の最初の求解には、期待値の拡張を持たない基本の ILP（019 の切り分けで約 43 ms）の解を初期解として渡す案も含める。下限より良い解が無ければ解なしになる部分問題は、その時点で打ち切ってよい。
  - (d) HiGHS の設定のうち 019 で試していないもの（例: `mip_heuristic_effort` を上げる。設定の名前は `highs` の `types.d.ts` の options から選ぶ）。
  - (e) 試作の中で見つけた工夫。採るときは、厳密さが変わらない理由を報告に書く。
- D2: 試作は、`packages/solver/src/main` を変えずに、測定専用のファイル `packages/solver/src/test/damagePrototype.measure.ts`（CI では実行しない）に書く。`buildModel`・`extendWithDamage`・`damageTargets` 等の既存の関数を読み、(a) は `extendWithDamage` の写しを試作のファイルの中で書き換え、(b) はマスターの防具・装飾品・生産護石を絞った写しを渡す。HiGHS の設定と目的の形は、現行の本実装と同じにする（`presolve` off・`mip_allow_restart` false・`blend_multi_objectives` false・θ と空き Lv の重みを補助の目的として優先度付きで渡す。`.claude/rules/solver.md`）。
  - 条件: 実データ・発動条件をすべて有効・マスターの先頭の武器・`maxResults` 10・`timeoutMs` 60 秒・必須スキル 3／6／10 個 × 解あり／解なしの 6 ケース（`solveBuilds.measure.ts` の `expectedDamage` のケースと同じ）・Node。護石は、なし（生産護石オフ）と、`support/craftedCharms.ts` の `topRankCraftedCharms`（生産護石オン。画面と同じ規則）の両方。
  - 実行: `pnpm --filter @swv/solver exec vitest run --mode measure --reporter=verbose --silent=false src/test/damagePrototype.measure.ts`。候補・ケース・回数は環境変数で絞れるようにする（`.claude/rules/solver.md` の測定の項。describe 名の `-t` で分けない）。候補のふるい分けは各ケース 1 回でよく、1件目までの時間の最大が小さい上位の候補（現行を含む）は各ケース 3 回測る。
  - 報告: 候補（と組み合わせ）ごと・生産護石のオンとオフごとに、ケースごとの1件目までの時間の最大と合計時間の最大、求解の回数、1件目の期待値が現行の実装と `DAMAGE_EPSILON` 以内で一致するか、10件の期待値の列が現行と一致するか（(b) を含む候補は 1件目だけ一致すればよい。Q41）を表で載せる。現行の実装も同じ条件で測って表の先頭に置く。1つの候補の測定が 1 ケースで 60 秒を超えるときは打ち切ってよい（報告に打ち切ったことを書く）。試作のファイルはコミットし、本実装（T5）で削除する。
  - 目安: 画面は Node より約 0.74 秒遅い（`design/tech-stack.md` の 007 の節）。Node での1件目までの時間の最大が約 2.2 秒以下なら、画面で 3 秒以下に届く見込みがある。合否は画面の測定（T6）で決め、Node の値では決めない。
- D3: 方式の決定は、T3 の報告を受けてメインがユーザーに確認し（設計判断のため）、確定した方式を本 plan.md の D9 に、試作の結果の要約を decisions.md Q50 の「判断材料」に追記する（T4）。判断の順は次のとおり: 生産護石のオンとオフの両方で Node の1件目までの時間の最大が約 2.2 秒以下の方式があれば、そのうち変更が小さいもの。無ければ、生産護石オンの1件目までの時間の最大が最も小さい方式。どの候補も現行より明らかに速くない（1件目までの時間の最大の短縮が 1 割未満）ときは、求解を変えない（D9 に「現行のまま」と書き、T5 は D5 の受入基準 4 の生産護石のテストの追加だけにする）。支配の除外（候補 (b)）は、採る方式に含まれるときだけ実装する（受入基準 2 は WHERE の条件つき）。

### 本実装（受入基準 1〜5）
- D4: 支配される候補（D9 で採るときだけ。受入基準 2）。対象は目的関数が `expectedDamage` のときの防具・装飾品・生産護石だけで、他の目的関数の候補は変えない（受入基準 3）。固定・除外（`fixedArmor`・`excludedArmorIds`・`excludedDecorationIds`）を適用した後の候補の中で判定する。
  - 関係するスキル: 必須スキル（通常・シリーズ／グループ）と、期待値の対象のスキル（`damageTargets`）。
  - 防具 X が防具 Y に支配される: 同じ部位で、関係する通常のスキルのレベルがすべて X ≤ Y、関係するシリーズ／グループの所属が X ⊆ Y、スロットが種別（`weapon`・`armor`）ごとに Lv を降順に並べて要素ごとに X ≤ Y（数が足りない側は 0 とみなす）。
  - 装飾品 X が装飾品 Y に支配される: 同じ種別で、関係するスキルのレベルがすべて X ≤ Y、装飾品の Lv が X ≥ Y。
  - 生産護石 X が生産護石 Y に支配される: 両方が生産護石（`request.charms` のうち、ID がマスターの `charms` にあるもの）で、関係するスキルのレベルがすべて X ≤ Y、スロットが防具と同じ比べ方で X ≤ Y。マスターに無い ID の護石（鑑定護石）は、外す側にも外させる側にもしない（スコープ外）。
  - 互いに支配し合う（関係する属性がすべて等しい）候補は、並び（防具・装飾品はマスター、護石は `request.charms`）で最初のものだけを残す（決定的にするため）。
- D5: テスト（`packages/solver/src/test/**`）。
  - 受入基準 1・3: 既存のテスト（`solveBuilds.damage.spec.ts`・`solveBuilds.spec.ts`・`solveBuilds.real.spec.ts`）を変えずに通す。**ただし例外が1件**（T5 で判明。2026-10-29 にユーザーが承認）: `solveBuilds.damage.spec.ts` の「同点の順（Q36）」は、マスターの `h-q`（slot Lv4）が `h-big`（Lv3）・`h-small`（Lv1）を支配し、D4 の除外で2件が消えるため、そのままでは通らない。テストのマスターを、支配し合わない同点（例: slot(3)+slot(1) と slot(2)+slot(2)）に組み替え、空き Lv の降順を確かめる意図を残す。同点の順のテスト（`solveBuilds.damage.spec.ts` の「同点の順（Q36）」）が変更なしで通ることを確かめる。通らなければ報告して止まる。
  - 受入基準 4: 生産護石（マスターの `charms` にある ID）を候補に含む手作りの小さなマスターで、総当たり（`support/bruteForce.ts`）の最大と1件目の期待値が一致すること、全件が独立の検算（`support/verifyBuild.ts`）に通って `score` が降順であることを確かめる。D9 が会心倍率の候補ごとの分解（候補 (a)）を含むときは、会心倍率の候補が 3 個以上で、真の最大が 1.25 以外の候補にある場合と、ε 以内の同点が別の部分問題にまたがる場合を含める。支配の除外を採るときは、支配される防具・装飾品・生産護石と互いに等しい候補を含むマスターで、2件目以降が D4 の候補の定義で総当たりした最大と一致することと、支配の判定の関数の単体テストも書く。
  - 受入基準 5: `expectedDamage` で、時計を進める `now` による時間切れ（それまでの構成と状態 `timeout`）、キャンセル（`SolveCancelledError`）、`onProgress` が返す構成と同じ並びで1件ずつ渡ることを、既存のテスト（`solveBuilds.damage.spec.ts` の「期待値の時間切れ・キャンセル・進捗」）で確かめる。D9 が1件に複数回の求解（部分問題など）を含むときは、件の途中の求解で時間切れ・キャンセルになる場合のテストを足す（途中の部分問題の解を返さないこと）。Worker の `progress` のメッセージは `worker.spec.ts` の既存のテストで確かめる。

### 画面の測定（受入基準 6・7）
- D6: 画面の測定ハーネス（`apps/web/e2e/measure/`）を、生産護石のオンとオフの両方で測る形にする（T1）。
  - `damage-ui.measure.ts`（`expectedDamage`）: 007 の条件（実データ・発動条件はすべてオン・マスターの先頭の武器・件数 10・候補のランクは下位と上位・6 ケース × 3 回・上限は画面の `SOLVE_TIMEOUT_MS`）のまま、「生産護石を候補に含める」をオンにした回とオフにした回の両方を測る。ケースごとの1件目までの時間と合計時間と状態・件数を出力し、生産護石のオンとオフのそれぞれと全体について、1件目までの時間の最大と、3 秒と 5 秒のそれぞれに対する合否を出力する（受入基準 8・9 の判定にそのまま使うため）。
  - `solver-ui.measure.ts`（`defense`）: 004 の条件のまま、生産護石のオンとオフの両方で、ケースごとの合計時間と状態を出力し、生産護石のオンとオフのそれぞれと全体の合計時間の最大と、3 秒に対する合否を出力する。
  - 状態の検査: 生産護石オフは現行どおり（解ありは構成が1件以上、解なしは解なしの表示）。生産護石オンの「解なし」ケースは、護石が増えて解が出ることがある（021 の測定）ので、構成あり・解なしのどちらも可とし、状態を出力する。どちらでもエラーの表示なら失敗にする。生産護石オンで構成が出た回の1件目までの時間も、最大の計算に含める（受入基準 8 の「全ケース・全回」）。
  - 測定は時間を検査（assert）せず、CI では実行しない（`playwright.config.ts` の `measure` プロジェクトのまま）。
- D7: 基準値の測定（T2。handoff の要確認事項）。T1 の後、求解を変える前に、メインが `pnpm --filter @swv/web run measure --workers=1` を実行し、現行の実装の画面の時間（`expectedDamage`・`defense`、生産護石のオンとオフ）を decisions.md Q50 の「判断材料」に追記する。T3 の委譲プロンプトに、この基準値を比較の材料として渡す。

### 記録（受入基準 8〜10）
- D8: `design/tech-stack.md` は、本実装の後の画面の測定（T6。T5 の後）でメインが書く（測定の結果が本実装まで決まらないため）。新しい節「ブラウザの Worker 上の expectedDamage の再測定（024 worker-solve-perf）」に、条件・環境・版・採った方式（D9）・試作して採らなかった方式と T3 の測定値の要約・024 の前の基準値（D7）・ケースごとの1件目までの時間と合計時間（`expectedDamage`、生産護石のオンとオフ）・`defense` のケースごとの合計時間（生産護石のオンとオフ）・それぞれの最大・合否を記録する。007 の節と 021 の節は残し、それぞれの冒頭に 024 の節への参照を1行足す。合否は次のとおり。
  - `expectedDamage` の1件目までの時間の最大（生産護石のオンとオフの全ケース・全回）が 3 秒以下なら合格。3 秒を超え 5 秒以下なら、基準を読み替えて合格と記録する（受入基準 9）。5 秒を超えたら不合格と記録し、T7 で次の対策を起票する。
  - `defense` の合計時間の最大が 3 秒を超えたら、記録して T7 で起票する。024 では `defense` の求解を変えない（受入基準 10）。
- D9: 採る求解の方式（T4。2026-10-29 にユーザーが T3 の報告から選んだ）: **候補 (b) 単独（支配される候補の除外。D4 の定義どおり、支配の除外を T5 に含める）**。会心倍率の候補ごとの分解（候補 (a)）・下限の受け渡し (c)・HiGHS の設定 (d) は採らない。HiGHS の設定と目的の形は現行のまま。
  - 理由: Node の1件目までの時間の最大が、生産護石オンで 4083 → 2420 ms（約 41% 短縮）、オフで 2699 → 2664 ms（約 1%）。画面の見込みはオン約 3.2 秒・オフ約 3.4 秒（Node + 約 0.74 秒の目安）。全体の最大を決めるのはオフ（k=3 解あり）で、`a-rebuild+b`（オン 2128 ms・オフ 2650 ms）と差が出ない一方、(a) は実装とテストが大きいため、変更が最小の (b) 単独を選ぶ。D3 の機械的な適用（オンの最大が最小の `a-rebuild+b`）とは異なる選択で、ユーザーが了承した。
  - 2件目以降の列は現行と変わりうる（019 Q41 で許容。1件目は全ケースで現行と一致）。T5 のテストは D5 の受入基準 2 の条件つきの記述どおり、D4 の候補の定義で総当たりした最大との一致で確かめる。
  - 合否は画面の測定（T6）で決める。3 秒に届かない場合は 5 秒への読み替え（D8）。
