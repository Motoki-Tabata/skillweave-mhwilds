# 024: worker-solve-perf

## 目的 / ユーザーストーリー
ハンターとして、火力（期待値）を最大にする構成の検索で、1件目の構成を数秒のうちに画面で見たい。いまは生産護石をオフにしても1件目が画面に出るまで最大 3.4 秒かかり（`design/tech-stack.md`「ブラウザの Worker 上の expectedDamage の測定（007 damage-ui・2026-10-26）」）、既定の生産護石オンでは 5 秒前後と見込まれる（Node で 4.5 秒。021 の測定）。024 では、厳密さ（006 decisions.md Q36）を保ったまま `packages/solver` の求解を速くし、画面での1件目までの時間を基準の 3 秒以内に収める。届かないときは、届いた値を記録して基準を読み替える（decisions.md Q50）。

用語:
- 1件目までの時間: 画面で「検索」を押してから、逐次表示の「構成 1」のカードが出るまでの時間（007 の測定と同じ）。HiGHS の初期化とマスターの読み込みを含めない。
- 合計時間: 画面で「検索」を押してから、検索中の表示が消えて結果（解あり・打ち切り・解なし）が出るまでの時間。
- 画面の測定: `pnpm --filter @swv/web run measure` で、007 と同じ 6 ケース（必須スキル 3／6／10 個 × 解あり／解なし）を各 3 回、実データ・発動条件はすべてオン・マスターの先頭の武器・件数 10・候補のランクは下位と上位で測ること。
- 支配される候補: 019 decisions.md Q41 の定義に、生産護石どうし（必須スキルと期待値に寄与するスキルのレベルとスロットが、すべて別の生産護石以下であるもの）を加えたもの。

## 受入基準（EARS記法）
- AC-1: WHEN 目的関数が `expectedDamage` のとき THE system SHALL 019 と同じく、必須スキルの下限を満たす構成のうち期待値が最大のものから順に返し、期待値が同点の構成は防具用、次に武器用の空きスロットの Lv の合計が大きいものを選ばなければならない（006 decisions.md Q36）。構成ごとの `score` には、返す構成から計算した期待値を入れなければならない。
- AC-2: WHERE `expectedDamage` で支配される候補を外すとき THE system SHALL 1件目の期待値を外さないときと一致させ、2件目以降は、支配されない候補の中で、それまでに返した防具と護石の組を除いた最大を返さなければならない（019 decisions.md Q41）。
- AC-3: THE system SHALL 目的関数が `expectedDamage` 以外のとき、024 の前と同じ候補・構成・状態を返さなければならない。
- AC-4: THE system SHALL `expectedDamage` で返すすべての構成について、ソルバーと独立に数え直した期待値が `score` と一致して降順に並ぶこと、生産護石を含む小さなテスト用のマスターで総当たりした最大と1件目の期待値が一致すること、2件目以降が AC-2 の候補の定義での総当たりの最大と一致することを、テストで確かめなければならない。
- AC-5: THE system SHALL 進捗の通知（`onProgress` と Worker の `progress` のメッセージ）で求めた構成を1件ずつ呼び出し側へ渡し、`timeoutMs` を過ぎたときはそれまでの構成を状態 `timeout` で返し、キャンセルされたときは `SolveCancelledError` を投げなければならない（019 と同じ扱い）。
- AC-6: WHEN 画面の測定を実行したとき THE system SHALL 目的関数 `expectedDamage` について、生産護石を候補に含める（既定のオン）とオフの両方で、ケースごとの1件目までの時間と合計時間を出力しなければならない。CI では時間を測ってはならない（decisions.md Q50）。
- AC-7: WHEN 画面の測定を実行したとき THE system SHALL 目的関数 `defense` についても、生産護石を候補に含めるとオフの両方で、ケースごとの合計時間を出力しなければならない（decisions.md Q50）。
- AC-8: THE system SHALL 画面の測定の結果と、採った求解の方式と、区間 C で試作して採らなかった方式の測定値を `design/tech-stack.md` に記録しなければならない。合格は、`expectedDamage` の生産護石オンとオフの全ケース・全回の1件目までの時間の最大が 3 秒以下であることとする（decisions.md Q50）。
- AC-9: IF `expectedDamage` の1件目までの時間の最大が 3 秒を超えたとき THEN システムは、基準を「1件目までの時間の最大が 5 秒以下」に読み替えて合否を記録し、5 秒も超えたときは、次の対策を `specs/open-questions.md` に新しい Q として起票しなければならない（decisions.md Q50）。
- AC-10: IF `defense` の合計時間の最大が 3 秒（004 の画面の基準）を超えたとき THEN システムは、その結果を記録して `specs/open-questions.md` に新しい Q として起票し、024 では `defense` の求解を変えてはならない（decisions.md Q50）。

## スコープ外
- 近似で候補を絞ってから並べ替える方式（006 decisions.md Q36 を変えない）
- 合計時間の短縮、画面の上限 30 秒（`SOLVE_TIMEOUT_MS`）と件数の既定の変更（decisions.md Q50 で合計時間は基準にしない）
- `defense` など `expectedDamage` 以外の目的関数の高速化（decisions.md Q50）
- Worker のメッセージや画面の描画の経路の高速化（Node との約 0.7 秒の差の切り分け）
- `apps/web` で生産護石を系統ごとの最上位ランクに絞る規則の変更（021 decisions.md Q77）
- 鑑定護石を併せた候補・装飾品の所持数の制限・件数 30 のときの測定
- 属性の期待値（open-questions.md Q40）
