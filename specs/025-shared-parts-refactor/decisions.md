# 025 shared-parts-refactor の決定記録

## Q73（決定: 2026-10-28）
- 問い: 端末保存のストア（`stores/charms.ts`・`stores/weapons.ts`）の状態機械を、どこまで共通化するか。
- 決定: 保存先（アカウントと端末）の状態機械の全体を、汎用の部品にする。部品が持つのは次のとおり。
  - 保存先の判定（認証の判定を待ってアカウントか端末かを決める）、端末の保存先を開く・一覧を読む、`ensureLoaded`・`reload`、読込の状態（読込中・読込済み・端末に保存できない・読み込みの失敗）と失敗の文言。
  - ログアウトと 401 での端末への切り替え、保存先が変わる前に送った要求の応答を捨てる処理、更新の 409・404 のあとの一覧の読み直し、削除の応答待ちの ID。
  - 保存（登録・上書き）と削除。保存に成功してから一覧を変える。
  - 種類ごとに違うもの（素のオブジェクトへの変換・スキーマ版・保存先を開く関数・API・トーストの文言）は、部品の引数で受け取る。
  - 護石はアカウントと端末の両方で使い、個体差のある武器は端末だけで使う（武器の API は 013 user-weapon-save で渡す）。武器も、削除の応答待ちの ID による二重の削除の防止を持つようになる。
  - 保存した構成（`stores/builds.ts`）はログインを要し、ログインが必要の状態を持つため、この部品を使わない。ID の降順の並べ替えの関数だけを共有する。
- 理由: 機能マップの 013 user-weapon-save は、武器をアカウントと端末に保存する、護石と同じ形のストアになる。端末の部分だけを共通にすると、013 がアカウントの部分を護石から複製するか、013 の中で共通化することになり、025 を先に行う意味が薄れる。いまの `charms.spec.ts`・`weapons.spec.ts` が、移行の前後で挙動が変わらないことを確かめる回帰のテストになる。

## Q74（決定: 2026-10-28）
- 問い: 武器のストアの `save`・`remove` の戻り値（いまは boolean）を、護石と同じ書込結果の型にするか。
- 決定: 護石と同じ書込結果の型（`saved`・`failed`・`conflict`・`notFound`・`expired`・`discarded`）にする。呼び出し側（`views/WeaponsView.vue`・`components/weapons/WeaponForm.vue`）と `weapons.spec.ts` の期待値を追従させる。画面の挙動は変えない。
- 理由: Q73 の部品の戻り値をそのまま返せる。013 で武器の API が 401・409・404 を返すようになったときに、型を変えずに使える。

## Q75（決定: 2026-10-28）
- 問い: 404・409 の例外を機能名の付かない汎用のものにしたとき、応答の `detail`（いまは "Charm not found"・"Build not found" など機能ごとの文言）をどう扱うか。
- 決定: いまの文言を保つ。汎用の例外は文言を引数で受け取り、呼び出し側がいまと同じ文言を渡す。`ApiExceptionHandler` のハンドラは 404 と 409 の1本ずつにする。
- 理由: API の応答の本文を1バイトも変えず、リファクタの前後で挙動が変わらないことを契約テストと API のテストで確かめられる。

## Q76（決定: 2026-10-28）
- 問い: 護石と武器の削除確認ダイアログを、011 の `components/common/DeleteConfirmDialog.vue` に寄せるとき、条件で変わる本文（アカウントの護石の「ほかの端末からも消えます」・検索条件で選んでいる武器の「選択も外します」）をどう渡すか。
- 決定: いまの `DeleteConfirmDialog` の `title`・`description`（文字列）をそのまま使い、条件で変わる文は呼び出し側で組み立てる。slot は足さない。`CharmDeleteDialog.vue`・`WeaponDeleteDialog.vue` は削除する。
- 理由: 3つの削除確認とも、本文は1つの文字列で表せる。部品を拡張せずに済む。
